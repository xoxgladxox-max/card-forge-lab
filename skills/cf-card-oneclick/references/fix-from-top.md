# 从头纠错：不从脚改起

适用：一键出卡交付后，作者提出修改时。

发现正文有错时，先问一句：**错是从哪一层开始的？** 找到最高的出错层，从那一层起往下逐层改，最后才改正文。上游没改对，只在 body 里打补丁，同一个错误会换个样子再长出来。

链条（从上到下）：规划 → 节点树 → 料源索引 → 模版 → 任务书 → 验收 → 正文。

改了规范（原则改名、节点改名、字段改名）时，同一轮里做三件事，三件都做完这次修改才算完成：

1. 全项目 grep 旧名（index、任务书、模版、口径）；
2. grep 脚本里写死的清单和字段；
3. 装配脚本跑一次 dry-run。

| 层 | 在树里是哪个文件 | 典型出错表现 | 从这层起必须依次改 |
|---|---|---|---|
| 规划 | 对话中呈报的 key、树形、已确认事项 | 体验锚点漏了或偏了；题材来源判错（衍生题材当原创写） | 规划 → 树 → 来源索引（获批后）→ 模版 → 任务书 → 验收 → 正文 |
| 节点树 | 卡根总纲一览表 + 目录 | 缺节点（只有分支没有基底）；内容挂错节点（角色内容挂进了 world） | 树 → 索引 → 模版 → 任务书 → 验收 → 正文 |
| 料源索引 | 作者批准的来源记录；未批准时在对话呈报 | 调研方向未确认；缺基底料；出处错；把角色说法当客观事实 | 来源 → 任务书 → 验收 → 正文 |
| 模版 | 各 skill 的模版文件；项目自带的模版副本 | 用错模版；自拟结构 | 模版 → 任务书 → 验收 → 正文 |
| 任务书 | 各节点工序段的「要产出」（交接包里是节点任务书） | 产出范围漏项；越界要求写别的节点的事；问题本身预设了错的前提（例：把一个角色独有的感知当成全卡文风来要求） | 任务书 → 验收 → 正文 |
| 验收 | 工序段「验收」行、cf-card-review、交接包验收表 | 漏检，让错误过了关 | 验收 → 重验所有受影响的正文 |
| 正文 | `<!-- body -->` 之后 | 上游都对，只是写错了 | 就地改 |

执行纪律：

- 改之前先在对话中呈报：哪层错了、为什么错、影响哪些节点；只有作者明确批准对应记录文件后才落盘。然后逐层改，每改完一层都给作者过目。
- 已确认的节点要重开，先经人同意。重开后状态退回「草稿」，依赖它的下游节点逐个复验。这是「只延伸不改写」唯一的例外，而且必须留痕。
- 错误根源在技能层（比如技能根本没规定这类节点的模版）时，项目里照常修，同时向人报告，建议修改哪条技能。只修项目不报告，等于下一张卡再犯一次。
- 禁止：上游没动只改正文；在正文里加「更正」「补充说明」段落；另建一个新节点去盖住旧节点。
- 被批评时先分清批的是哪一层：批的是内容就换内容，已定的结构节点不因此撤掉。要删节点，先备份。
