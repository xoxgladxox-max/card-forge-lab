# 一键出卡

本技能只有一个作者确认点，即第 0 步「确定需要什么」。确认之后，本流程一直跑到交付，中途不提问、不等确认。各领域技能里写的「停下问作者」「作者确认后才继续」「拍板」，在本流程里一律改为：**照常判断，把需要作者决定的内容标成【提案】或【缺口】，继续往下做，最后在交付报告里统一列出。**

这样做并不违反「研究结果不是结论，建议不是裁决」：中途产生的推断全部带标记写入，作者在交付后可以逐条采纳、改写或删除，没有任何一条被写成作者已确认。

## 第 0 步：确定需要什么（唯一的提问）

先从用户的输入里提炼「玩卡时想直接体验到的内容」，列成体验 key。用户已经说清的项不再问。其余项用一次提问问齐，不逐条追问：

| 项 | 决定什么 | 典型选项 |
|---|---|---|
| 体验 key | 整张卡围绕什么写；之后建的每个节点都要能对应到其中一条 | 场景、关系、冲突、互动方式、感受方向 |
| 题材来源 | 世界节点写几层 | 原创世界 / 已知作品正传 / 已有作品的衍生、IF、二创 |
| 资料 | 走填充还是引导；去哪里查 | 原作名和角色名、本地资料文件夹、已有卡、没有资料 |
| 角色戏份 | 角色从哪一档模版起步 | 配角 mini / 主力 standard / 长线主角 full |
| 需要的部分 | 哪些节点要建 | 世界书、配角、文风、回复格式与状态栏、开场白（几条）、亲密模块 |
| 产物形态 | 装配成什么 | 纯文本 / 酒馆 JSON / PNG；世界书内嵌或独立 |
| 工作位置 | 节点树和成品放在哪里 | 卡工作文件夹路径；已有卡时写原卡位置 |

边界情况（资料半全、改已有卡、升降档、要英文输出）按 `references/routing-matrix.md` 判断，把判断结果写进这次提问的选项里，而不是之后再问。

用户回答后，把以上各项整理成「出卡单」写在对话里。出卡单里同时列出这张卡的结构提案：各领域技能里的模板都是示例，这里写明世界、角色、状态栏等要用哪些块、去掉哪些、新增哪些。出卡单就是本次运行的作者确认。之后的所有步骤只在出卡单范围内做，不扩大范围；做到一半发现结构要变时，标【提案】继续，交付时列出。

## 自动阶段：调研 → 世界书 → 角色 → 配套 → 审查 → 装配

| 阶段 | 读哪个技能 | 产出 | 本流程里的处理 |
|---|---|---|---|
| 1 调研 | cf-card-research | 来源记录、事实矩阵、缺口清单 | 至少两源交叉。查不到的写进缺口，不凭印象补 |
| 2 世界书 | cf-card-worldbook | world / location / rule / item / lore 节点；条目触发配置 | 题材来源按出卡单定层数；世界节点在角色之前完成 |
| 3 角色 | cf-card-character | character / module / corpus 节点 | 按直通式走，所有关口报告不停顿，并入交付报告 |
| 4 配套 | cf-card-format-export | style / output / greeting 节点 | 只做出卡单勾选的部分；有状态栏时先定状态栏，再写开场白 |
| 5 审查 | cf-card-review；表达问题按 cf-card-refine 改 | 审查报告 | 能就地修的表达问题直接修；涉及事实、归属、上游层的问题不改，记入交付报告 |
| 6 装配 | cf-card-format-export 第四、五部分 | 卡文件、世界书、校验结果 | 原卡先备份再写；跑两个校验脚本并回读 |

阶段之间只看上一阶段的产出，不回头重做已完成的阶段。发现上游问题时，在出问题的节点里标【缺口】或【提案】并继续，不在下游正文里打补丁掩盖。

## 自动阶段中的标记

| 标记 | 什么时候用 | 写在哪里 |
|---|---|---|
| 【缺口】 | 需要的事实查不到，或资料互相冲突 | 节点正文对应位置，只写缺什么，不写猜测的内容 |
| 【提案】 | 需要作者取舍，本流程先选了一种 | 节点正文对应位置，写明选了什么、另有哪些选项 |
| 【角色说法】 | 内容只是某个人物的说法，不是客观事实 | 只放在该人物自己的节点里 |

每条事实保留来源和说话者。没有来源的内容不写成事实；旧稿只当线索，不当证据。

## 以下情况仍然会停下

一键不等于什么都不管。遇到下面的情况立即停止并报告，不用貌似完整的产出掩盖：

- 用户说停止、先纠正，或改变了出卡单的内容。
- 写入位置超出出卡单给定的工作位置，或要覆盖一个无法备份的文件。
- 工具失败导致后续步骤无法真实执行（读不到资料、校验脚本无法运行、写入失败）。
- 关键资料一条都没有，整张卡只能靠编造写成。

## 卡的节点树

一张卡对应 `cards/<卡名>/` 下的一个文件夹。每个设定是一个 `.md` 节点文件，节点有类型。世界书条目放在 `world_book/` 下（可按子目录分组或平铺），层级关系写在标题和正文里。树只负责组织和导航，层级关系不会进提示词，导出后每条内容各自独立注入。

```
cards/<卡名>/
|-- card.md                       # card：卡名、世界书名、留在卡里的扩展设置
|-- description.md                # 单槽字段（output / character 等，空字段不生成）
|-- system_prompt.md              # 单槽字段（按需生成）
|-- message/
|   |-- 0.md                      # first_mes（主开场白）
|   `-- 1.md                      # alternate_greetings（备选开场，从 1 起）
|-- world_book/
|   |-- world/                    # 世界、地点、规则、道具、历史
|   |   |-- 基底世界.md
|   |   |-- 分支世界.md
|   |   |-- 某地点.md
|   |   `-- 某时间线.md
|   |-- character/
|   |   |-- 主角色.md             # 定死：人格、外貌、言语、行为逻辑
|   |   |-- 主角色特化模块.md     # module：名字带所属
|   |   |-- 主角色语料.md         # corpus
|   |   `-- 配角.md
|   `-- style/
|       |-- 基底文风.md
|       `-- 特化文风.md
|-- regex/                        # 拆出的正则（<序号>-<名>.json + .html）
|-- scripts/                      # 拆出的脚本（<序号>-<名>.json + .js、variables.json、xiaobaix-tasks.json）
`-- character.png                 # 角色卡封面图
```

以上是中立的结构示例，节点文件名换成当前卡的实际内容。module、corpus 放在 `world_book/character/`（或直接平铺在 `world_book/`），所属写进名字和 part。同组顺序默认按文件名，要调整就在节点头上写 order，不改名。

| 类型 | 是什么 | 导出去处 |
|---|---|---|
| `card` | 卡根：`card.md`（卡名、世界书名、留在卡里的扩展设置） | name 和卡元信息 |
| `world` | 世界观；基底和分支各一个节点 | 世界书常驻条目 |
| `location` | 地点，所属写进正文 | 世界书触发条目 |
| `rule` | 机制或规则，正文写明在哪一层生效 | 世界书触发条目 |
| `item` | 关键物 | 世界书触发条目 |
| `lore` | 历史、时间线、背景设定 | 世界书触发条目 |
| `character` | 角色；主角配角同型，配角只有一个 `.md` 文件 | 主角进世界书常驻条目；配角进触发条目；`description.md` 留给本卡元提示词 |
| `module` | 角色子模块（特化玩法、专属机制） | 触发条目，可配二级过滤 |
| `corpus` | 语料：台词锚点、对话示例 | 随角色进同一条目，或单独成触发条目（不用 mes_example） |
| `style` | 文风；基底常驻，特化带使用条件 | 世界书文风层条目 |
| `output` | 输出规范：思维链、状态栏、语言原则 | `description.md` / `system_prompt.md` / `world_book/` 低深度条目 |
| `greeting` | 开场白，`message/0.md` 起每个文件一条 | first_mes / alternate_greetings |
| `plot` | 剧情：按场次推进的剧情底稿，包裹 `<plot name="…">` | 世界书触发条目，5xx |
| `event` | 事件：会改变当前局面的事件、压力档位、随机事件池，包裹 `<event name="…">` | 世界书触发或概率条目，5xx |
| `wiki` | 设定百科：词条式的术语、组织、地名速查，包裹沿用 `<lore name="…">` | 世界书触发条目，5xx |

类型存在的依据是酒馆卡有对应的槽位，或本工作流约定的世界书分组。势力组织用 `character` 写；剧情用 `plot`、事件用 `event`、设定百科用 `wiki`（归「其余」5xx 组）；机制本身（如压力档位怎么推进）仍用 `rule`。除此之外不另造类型。`调研.md`、`记录/`、`候选/`、`待归位/`、`note/`、`backups/`、`dist/` 不进卡。

每个节点正文自包含，不写「如前所述」；一件事只在一个节点里写，别处只引用。树定义的是形状上限，不是必填清单：配角一个 `.md` 文件就够；是否拆分看三点，即体量大不大、有没有按需加载的场景、拆开能不能真正省篇幅。

## 交付报告

跑完后在对话里交一份报告，按以下顺序：

1. **出卡单**：第 0 步确认的内容，原样复述。
2. **产出清单**：建了哪些节点（节点 / 类型 / 导出去处 / 一句话），成品文件路径，原卡备份路径。
3. **待作者处理**：全部【提案】和【缺口】，逐条写节点、内容、选项或缺什么。这是作者交付后最主要的工作。
4. **审查结果**：审查中发现但没有改的问题，写明最早出错在哪一层。
5. **机器结果**：两个校验脚本的结果和回读结果。

报告里以下状态分开写，不互相替代：

- 机器校验通过：只说明格式和装配没问题。
- 已完成规定检查：只说明流程跑完。
- 待作者处理：仍有提案或缺口。
- 作者已确认：只有作者看过并明确确认后才这样写。本流程跑完时，除出卡单以外的内容都不是这个状态。

## 交付后的修改

作者看完报告后提出修改时，不再按一键模式自动跑，按 `references/fix-from-top.md` 从最早出错的层往下改。作者只采纳或删除某条【提案】时，直接改对应节点，再重新装配一次。
