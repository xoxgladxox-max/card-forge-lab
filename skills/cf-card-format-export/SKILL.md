# 配套

本技能包含世界和角色以外、一张卡还需要的部分：文风、开场白、回复格式，以及最后的装配导出。各部分彼此独立，按需要读对应一节。

**模板是示例。** 文风块骨架、状态栏字段、篇章生成器骨架都只是起点：动笔前先按这张卡提出结构提案（用哪些块、记哪些状态、怎么排），作者确认后再写。例外是第五部分的卡文件格式：V2/V3 字段、PNG 数据块是酒馆的导入要求，照规范来。

# 一、文风块

文风不是「写得好看」，是「设计得好生成」。AI 默认会往训练分布的中间值靠：冲突浓度拉满、对话扁平、总结式抽象、碎句成行。文风设计做的是四件事：把世界压回常态、把文风锚成坐标系、把素材当参照物、只写偏离项。

### 一、世界分层：常态占绝对主体

任何题材都按三层搭，常态是主体：

```
第三层  突发冲突与暗线（约 10%）   特定角色的暗手、危机引爆——只是匕首，不是世界底层规则
第二层  题材特异载体               该世界特有的媒介、制度、技术，对里面的人是「理所当然」
第一层  基底秩序（约 90%）         真实可信的日常：语言、作息、空间、物件
```

三条硬规则：
- 常态先立住。冲突的力量来自对正常生活的打破；90% 不扎实，10% 的破坏就没有痛感。
- 第二层是日常工具，不是奇观。虚拟配信、魔法、机甲，对角色来说就是书包里的手机。
- 暗线只是暗线。某个角色的手段（录音、社死威胁、操控人心）是局部引爆点，禁止泛化成全员高压、人人勾心斗角。

检查方法：连续写三场日常戏（上学、社团、吃饭），任何一场必须靠冲突才能成立，就是常态没立住。

### 二、文风坐标系三步

禁止用「有质感」「文艺」「高级感」这类模糊词定文风。

1. **命名锚定**：用具体作家名 / 作品名 / 流派名。示例：日系青春群像 → 武田绫乃《吹响！上低音号》、绫奈由仁子《It's MyGO!!!!!》；硬汉派 → 钱德勒《漫长的告别》；中式古典白话 → 张爱玲、白先勇。
2. **提炼可操作特征**：把坐标拆成可执行、可检查的描写习惯，每条是动作或结构。示例：群体中视线交错与话没说完的停顿、动作时的肌肉与呼吸细节、台词只露水面重压藏在没说出口的部分、环境光影与情绪融合。
3. **负面排除**：每种文风列一到两条绝对禁止的写法，用刚性动词。示例：日系青春群像严禁电报体短句成行（「停了一下。又停了一下。笑了笑。」），动作与视线必须融进完整的环境与心理空气。

示例对照（「停下 + 观察 + 暗笑」）：
- ❌ 碎句：她停下了。/ 她看着手机。/ 嘴角扬起。/ 很可怕。
- ✅ 融入：换气扇规律的嗡鸣把两人之间的空白拖得很长。她的指尖在亮起的屏幕上轻轻一滑，视线越过谱架边缘扫过来，右嘴角那颗细小的痣随着浅淡的笑意微微上提。

### 三、外语素材的等价重构

素材（外语台词、口癖、拟声、方言）是语感节奏与心理密度的参照物，不是待翻译的源文本。

四步：识别功能（这句在场景里承担什么：压迫、拉近、反差、仪式感）→ 理解密度（轻飘飘的撒娇还是坠着寒意的宣判）→ 用目标语言的句式节律、语气词、神态动作重新造出等价效果，不字对字翻 → 必要时在设定里保留原语关键短语作锚点（如 `ゲス顔`）。

硬性禁止：音译拟声（「库库库」「阿哈」）——换成目标语言里的喉音、气声、呼吸停顿或嘴角肌肉的白描；字面直译丢节奏——保住词义丢了语气等于白写。

可迁移技巧（示例，按卡调整）：
- 一人称双轨：表演态（撒娇、装无辜、营业）自称名字或昵称，真心态（逼问、宣示、撕开伪装）切换为「我」。人称切换本身就是文风。
- 设问出题式推进：提问 → 公布答案 → 答案即攻击 → 逼对方表态 → 沉默当作同意。掌控感从句式里长出来，不用旁白解释。

### 四、写文风块的工程规则

1. **只写偏离项**：AI 已掌握的通用常识一律不写，只写偏离通用认知的特异规则。写多了是噪音，噪音稀释权重。
2. **真实标签锚定**：用对应圈子（Pixiv / 日推 / 中文二创 / 英文 fandom）已验证的高密度标签唤醒模型的潜在语料，比长篇地文高效。标签与维度是题材专属内容，写在那张卡自己的文风设定里，不写在本技能。
3. **给维度不给路径**：定义两极坐标（表演态 vs 真心态、掌控端 vs 臣服端），不锁死具体动作与固定情节；列出的部位、道具、动作、台词只是可能性之一，等价物同理适用。
4. **奖赏稀缺**：夸奖、温柔、甜头在权力互动里是受控的稀缺筹码，越吝啬，给出的瞬间冲击越强。
5. **每个规则块问一句**：它服务于哪个体验锚点？不服务任何锚点的就是噪音。
6. **视角纪律**：第三人称受限视角，镜头只聚焦现场，严禁替 {{user}} 写动作、心理、决定；角色的里人格只在死角、独处、背对他人时浮现，人前维持表层——反差藏在视角纪律里。
7. **指令性与指导性分开**：红线与边界用「严禁」；可能性空间用「可以」「倾向」「重点放在」，留给 AI 按剧情与角色自适应推导的余地。

### 五、文风块骨架

```xml
<style name="[文风名]">
[一两句：本块在什么场景下用、不用时完全安静。基底文风常驻可省这段，特化文风必写]

本块为可能性空间，不是任务清单。按实际剧情与角色性格自适应，示例仅供参考，禁止照抄固定句式。

## 标签锚定
[真实圈子标签，按题材]

## 核心倾向
[本风格最在意的感觉、落差、权力关系或节拍，两到四条]

## 感官
[五感各给一组注意力去向：摸得到的 / 闻得到的 / 尝得到的 / 听得到的 / 身体内部的。写部位与物理属性，不写主观感受词]

## 描写指导
  [维度 1]：[原则一句] + [可以 / 倾向做什么] + [启发示例，标明是示例]
  [维度 2]：……

## 描写重点
- [两到四条，本块独有的]

## 元原则
- 可能性空间声明、成年限定、激活边界（特化文风）
- 全局禁令不在这里重复，只写本块专属的
</style>
```

默认整块一条。只有满足本技能第四部分第 3 条的三明治护栏时才拆：「标签锚定 / 核心倾向 / 感官」进 XML 头，「描写指导」各维度拆成子项，「描写重点 / 元原则」进 XML 尾。

### 六、输出结构（三层骨架）

1. 正文：沉浸式叙事，不可省。
2. 条件触发块：只在剧情涉及特定媒介事件（直播、舆论、录音）时出现。
3. 状态栏：回复末尾，代码块展示场景、表里状态、关系指标、在场道具；数值变动必须带正文因果。

### 七、自检

- 世界观：当前场景有 90% 常态质感吗？有没有全员高压？
- 坐标系：用具体作家/作品/流派锚定了吗？负面禁止项列了吗？
- 句式：段落舒展吗？碎句成行清了吗？动作融进环境光影与心理了吗？
- 素材：外语素材等价再造了吗？音译与直译清了吗？
- 视角与反差：压迫感是否通过对方视角与微动作侧写呈现？表里反差有没有人称分工和隐秘性纪律撑着？
- 偏离项：还有 AI 默认常识的冗余吗？每条规则服务于哪个体验锚点？

# 二、回复格式与状态栏

本技能写的是一张卡里「AI 每轮回复该长什么样」的那部分规则：回复由哪几块组成、怎么收尾、要不要思维链、状态栏记什么、用什么人称和语言。

不管的事：角色是谁、世界怎么运转、文风偏向什么，这些各有归处。这里只管回复的形状。

### 先定这几项

写之前向作者问清楚，没定的不替作者定：

1. 每轮回复由哪几块组成，按顺序列出。例：正文 → 状态栏；或者 思维链 → 正文 → 状态栏。
2. 要不要状态栏；要的话，记哪些状态。
3. 要不要思维链；要的话，思维链的内容给不给使用者看。
4. 叙述人称和视角：第二人称写 {{user}}、第三人称写角色，或其他。
5. 正文语言、对白格式；需要保留原文的专有名词。

只写偏离默认的项。模型本来就会做的（分段、给对白加引号）不写。

### 放在卡的哪里

| 位置 | 特点 | 适合放 |
|---|---|---|
| `description` | 和本卡元提示词写在一起，每轮都带上 | 最核心的几条：不代写 {{user}}、停在哪里、叙述人称 |
| `system_prompt` | 替换使用者的主提示词；同样可能被预设挡住 | 完整的输出规范 |
| 低深度世界书条目、角色备注（depth_prompt） | 不受预设开关影响，按深度插进聊天记录 | 换了预设也必须生效的格式，例如状态栏模版 |

本工作流不写 `post_history_instructions`。

同一条规则只放一处。放两处时，改了一处忘了另一处，模型会拿到两套互相打架的要求。

### 回复结构与收尾

- 回复的各块按固定顺序出现，每块有明确的开头和结尾标记（例：状态栏用一对 XML 标签包起来），方便正则隐藏或美化。
- **收尾停在交给 {{user}} 的地方**：角色说完、做完这一轮，停下。不代写 {{user}} 的台词、动作、心理，不替 {{user}} 做决定。
- 长度给范围，不给最低字数。最低字数会逼模型灌水、复读。
- 不在规则里预写剧情走向。「这一轮要推进到某某事件」属于剧情安排，不是输出格式。

### 思维链

- 只在确实需要时加：状态多、需要回合间核对的卡；或模型容易写偏、需要先对照规则再动笔的卡。模型自带推理功能时，一般不再另加。
- 思维链写成**核对步骤**，不写成剧情草稿。例：核对 {{user}} 这一轮做了什么、哪些状态要变、有没有越过角色边界。
- 用固定标签包起来（例：`<thinking>…</thinking>`），配一条正则把它从显示或后续上下文里去掉，否则会占上下文，模型还会模仿上一轮的思考。
- 步骤三到五步，只列要核对的项，不列答案。

### 状态栏

- **只记需要跨回合保持、或本轮确实变了的状态**：日期、时间、地点、服装变化、持有物、伤势、关系变量这类。静态外貌、没变的衣物、正文里能直接看出来的心理，不进状态栏。
- 字段规则写「这个字段记什么、什么时候变」，不把正文描写、情绪结论或固定剧情流程塞进字段。
- 状态没变时允许沿用上一轮的值、简写或省略，不要求每轮重写。
- 好感度、信任度这类数值只表示当前状态，变化必须有事件依据；数值高低不等于唯一的心理或剧情走向。
- 需要追踪的才建字段，不为了「像游戏」而加。
- 卡有开场白时，开场白末尾带一份初始状态栏，格式和规则里的模版完全一致，模型会照着第一条往下写。

### MVU 变量

MVU 是用脚本把状态存成变量、每轮由模型输出更新语句的做法。本技能只管「记多少」，原则和状态栏相同：只建跨回合要用的变量，只记当前值，变化要有事件依据。

脚本安装、变量初始化文件、更新语句的具体语法不在本技能里，见缺口。

### 语言规范

- 写明叙述人称、视角、正文语言；需要保留原文的专有名词列成清单。
- 对白、动作、心理用什么格式区分（引号、星号、括号），选一种写明，全卡统一。
- 只写和默认不同的地方，一条一句。

### 交付前自查

- [ ] 上面「先定这几项」都有作者的答复，没有替作者定的项。
- [ ] 每条规则只出现在一个位置。
- [ ] 没有最低字数，没有预写剧情。
- [ ] 收尾规则写明不代写 {{user}}。
- [ ] 状态栏每个字段都说得出为什么要跨回合记。
- [ ] 例子都标了「例」。

### 缺口

- MVU 的技术接入（脚本、初始化文件、更新语法、配套正则）尚未整理核实。
- 小白X（LittleWhiteBox 扩展）的接入方式尚未调研。
- 思维链对不同模型的实际效果没有实测记录。

# 三、开场白

开场白是聊天里的第一条 AI 消息。本技能管它怎么写：交代什么、留什么、几条之间怎么分工。

### 酒馆里开场白的实际行为

- `first_mes` 是首条；`alternate_greetings` 里的每一条是首条消息的左右滑切换，使用者滑到哪条就从哪条开局。
- `first_mes` 为空时，第一条备选顶上去当首条。
- 开场白显示前会先过一遍作用于 AI 输出的正则，所以状态栏之类的块在开场白里也会被同一套正则隐藏或美化。
- 开场白之后就是聊天记录的一部分。**模型会照着它的长度、人称、格式和口吻往下写**，所以开场白就是整张卡回复格式的第一个样板。

### 先定这几项

1. 开几条：首条一条，备选几条。
2. 每条是什么开局：时间、地点、两人此刻的关系位置。
3. 叙述人称、视角、正文语言、对白格式。卡里已有规定的照用，没有的先问作者。
4. 卡有没有状态栏；有的话，初始值是什么。
5. 首条要不要写成篇章生成器，见「篇章生成器」。

### 一条开场白要交代的

- **场景**：在哪、什么时候、周围有什么，写到能让 {{user}} 知道自己站在哪里就够了。
- **角色此刻在做什么**：用动作和台词表现，不写成人物介绍。
- **停在需要 {{user}} 回应的时刻**：这一刻发生完就停，例如角色的一句问话、一个递过来的东西、一件刚发生还没处理的事（例子只是参考，换成当前场景里的东西）。停下之后不再补氛围收尾或引导句。
- **初始状态栏**：卡有状态栏时，放在末尾，格式和规则里的模版一字不差。

### 前提要有出处

开场白里交代的处境、起因、身体状态、时间压力，每一条都要在原作或已经确认的设定里找得到出处。

- 找得到：照着写。
- 找不到：改成开放写法，只写现象，不定死原因。例：写「送来得比平常晚」，不写「断供了」。
- 为了营造气氛编出来的前提，常常和人设相反，还会替 {{user}} 把剧情走向定死。这是开场白最常见的错。

### 用原文开场

- 原作里有合适的场面，优先直接用原文，照原作的句式和节奏，不改写成缩写或平铺的旁白。
- 标了「原文」就必须逐字对得上：用脚本从料源文件按起止句截取，写入后核对正文是料源里的一段；核对不过，不许标原文。
- 停在原文里的自然停点，不在后面续写。
- 原作没有对应段落、只能自写的，照原文风格写，并在节点里标明是自写。

### 不能做的

- 不代写 {{user}} 的台词、动作、心理和决定。开场白里 {{user}} 最多是「在场」，做什么由 {{user}} 自己写。
- 不替 {{user}} 定剧情走向。开场白给的是局面，不是结局或下一步安排。
- 不在开场白里做人物介绍、世界观讲解；这些在卡的其他部分，开场白只演一场戏。
- 开场白不加 XML 包裹。开场白是回复格式的样板，包裹会被模型学进正文。

### 首条和备选怎么分工

- 首条放最能代表这张卡的开局，也就是大多数人会玩的那一种。
- 备选各开一个**不同**的局面：不同时间点、不同地点、两人不同的关系阶段、不同的事件起点。只改几句措辞的备选没有意义。
- 每条都能单独成立：不依赖使用者看过首条，也不互相引用。
- 各条的人称、格式、状态栏模版保持一致，长度差不多；某一条写得特别长，从那条开局的聊天也会跟着变长。

### 篇章生成器

- 如果卡有两条以上不同的开局，或者玩家可以选扮演哪一方，那么 `first_mes` 写成篇章生成器：一段原文引子加一个 yaml 选择器，让玩家自己选开局和视角。
- 结构、选择器写法、骨架和配套要求见 `references/generator-template.md`（示例，按这张卡调整）。
- 用了生成器，本技能里对首条的要求——代表性开局、末尾状态栏、做回复格式的样板——改由第一条备选和玩家选完后的第一场承担。

### 称呼与宏

- 指代使用者用 `{{user}}`，指代角色用 `{{char}}` 或直接写角色名，全卡统一。
- 不用来源不明的宏；要用 `{{random}}` 这类非核心宏，先确认目标环境支持。

### 交付前自查

- [ ] 每条的每个前提都能说出出处，说不出的已改成开放写法。
- [ ] 没有一句替 {{user}} 说话、行动或做决定。
- [ ] 每条停在需要 {{user}} 回应的时刻，后面没有补写的收尾或引导句。
- [ ] 标「原文」的每条都用脚本核对过，确实是料源里的一段。
- [ ] 备选之间开局各不相同，每条都能单独成立。
- [ ] 人称、格式、状态栏模版与卡的规定一致。
- [ ] 用了篇章生成器的：选择栏留空，篇章与备选一一对应，代码块后没有收尾句，输出规范里有接续那一句。
- [ ] 例子都标了「例」。

# 四、装配：内容放进卡的哪里

1. **一节点一条目**：`world_book/**/<条目>.md` 正文 = 条目 content，元信息头 = 触发配置。`greeting` 放在 `message/<n>.md`（`0.md` 为 `first_mes`，`1.md` 起为 `alternate_greetings`），单槽字段放在顶层 `<字段>.md`（`description.md`、`system_prompt.md` 等，空字段不生成），`note` 不导出。creator_notes、post_history_instructions、tags、mes_example 默认不写。
   - 一个节点要出多条条目时（例：配角群里每人一条），每人一个 `.md` 文件放在 `world_book/character/`（或 `world_book/`）下，不在导出后另跑脚本拆——导出后才拆出来的条目，构建记录里的指纹对不上。
   - 进世界书的 character 节点放在 `world_book/` 下（或显式写 `target: character_book`）；`description.md` 由 output 节点写本卡元提示词。corpus、output、greeting 也要写明去处或按规定目录放置。
2. **层级对应注入深度**：世界观与社会规律 @D4（最深的背景）→ 机制与冲突规则 @D3 → 角色与剧情 @D2 → 文风 @D1 → 输出规范 @D0（最贴近末尾）。深度写在节点元信息头，导出时照搬。
3. **三明治是可选的，默认每条自包含**。要用时（例：多条模块共用一个总纲框），开头、收尾各建一个节点放在同一父目录下，头字段写 `wrap: head` / `wrap: tail`，并满足：首尾常驻、`ignore_budget: true`、与组内条目同一 position 与深度、开头 order 在组内最小收尾最大。不满足时酒馆会把首尾拆散（超预算先丢开头、位置不同拼不到一起）。护栏齐全也挡不住用户自己挂的全局世界书条目插进中间。
4. **条目要能单独看懂**：单独成条的内容都有带名字的顶层包裹，包裹里的 YAML 顶格写；元信息头写 `title`，它就是酒馆世界书列表里看到的标题。交付前按酒馆里看到的样子逐条过一遍标题、包裹首行和尾行。标签按下表（标签表只在这一处）：
   - 标签名按节点类型取固定的英文小写词，不带作品名或人物名；名字写进 `name` 属性，是这个人的哪一部分写进 `part`。同类多条同时加载时靠 name 分清。
   - title 用最短的自然叫法，不写路径，全卡不重复。只有不加范围就分不清时才加范围（例：时间线分原作基底和 IF 分支两条，所以分支那条写「某分支世界时间线」）；其余一律不加范围词（例：临海市、港口研究所、绫音、绫音口癖语料）。通用名（时间线、历史、势力格局、魔法体系这类每个世界都有的东西）单看认不出是哪一层，要加所属层的范围词（例：分支独有的时间线写「某分支世界时间线」，只写「世界时间线」会被当成原作的）。满屏同一个前缀不好看，所以只在认不出归属时才加。title 不要求复述 `name` 或 `part` 全称；`name` / `part` 用来归属和区分，title 只负责给人自然、可辨认的列表名。
   - 包裹内部不再套标签；多块并列（配角群）每块各自成对。输出侧标签（状态栏、思维链）由输出规范自己定。

   | 节点类型 | 包裹 | title 例（照本卡改写） |
   |---|---|---|
   | world / location / lore / rule / item | `<world name="…">`，其余同形，标签名即类型名 | 临海市世界观（顶层）、临海市世界时间线 |
   | character | `<character name="人物名">` | 绫音 |
   | module / corpus | `<character name="人物名" part="模块名">` | 绫音口癖语料 |
   | 配角群（一条多人） | 每人一个 `<character name="…">` | 配角群 |
   | style | `<style name="文风名">` | 雨季文风 |
   | plot（剧情） | `<plot name="…">` | 出罐与初见 |
   | wiki（设定百科） | `<lore name="…">`（沿用 lore 标签） | 16Lab |
   | event（事件） | `<event name="…">` | 物资被截 |
   | output | 进 description 不加包裹；进世界书用 `<output>` | 输出规范 |
   | greeting | 不加包裹（开场白是回复的样板） | — |
5. **装配与校验**：卡本体字段、JSON / PNG 载体按第五部分，跑 `scripts/validate-card.ps1`；世界书条目（触发逻辑、位置枚举、递归开关）按世界书条目机制，跑 `scripts/validate-worldbook.ps1`。两个校验分别跑。
6. **排序**：世界书条目按组连续编号，不重复：世界（world / location / lore / rule / item）1xx → 人物（character / module / corpus）2xx → 文风 3xx → 输出 4xx → 开场白及其他（greeting / plot 剧情 / event 事件 / wiki 设定百科）5xx；世界归世界、人物归人物，不穿插。check 只看 type 不看内容；报「格式适配提醒」时按内容确认 type，再适配标签和 order。组内按节点树先父后子，父子条目挨在一起。节点不写 order，由导出工具自动编；一组超过 99 条全卡改四位编号（1001 起）。超预算时酒馆先保留 order 大的，世界组最先被挤掉，大世界书里关键的世界条目设 `ignore_budget: true`。

# 五、装配：卡文件格式

一张酒馆角色卡就是一个 JSON 对象：放在 `.json` 文件里，或者塞进 `.png` 图片的文字数据块里。本技能管这个对象的**外层**：有哪些字段、每个字段在酒馆里起什么作用、怎么把现成内容装进去、怎么做成 PNG、怎么检查。

不管的事：卡里的内容写得好不好；`character_book` 里面条目怎么配（本技能只保证它是个带 `entries` 数组的对象）。

### 三种载体

| 载体 | 怎么存 | 酒馆的行为 |
|---|---|---|
| `.json` | 文件本身就是卡对象，UTF-8，不带 BOM | 有 `spec` 字段就按 V2/V3 读 `data`；没有 `spec` 但有 `name` 就按老的 V1 读；还认 Pygmalion 的 `char_name` 格式 |
| `.png` | 图片的 tEXt 数据块，关键字 `chara`（V2）或 `ccv3`（V3），值是卡 JSON 先转 UTF-8 再转 base64 | 读取时 **`ccv3` 优先**，没有才读 `chara`；酒馆自己导出 PNG 时两块都写，`ccv3` 那份只把 `spec` / `spec_version` 改成 V3 |
| `.charx` | V3 的 zip 包，根目录 `card.json`，素材放 `assets/` | 酒馆能导入；本技能只认识，不产出 |

改 PNG 卡时只替换 `chara` / `ccv3` 两块，其余数据块一字节不动，图片本身不重新编码。生成和替换都用 `scripts/embed-png.ps1`，见「生成 PNG 卡」。

### 用 V2 还是 V3

- **默认用 V2**：酒馆内部按 V2 存卡；V3 的 JSON 导入后也是按 `data` 读，V3 新增的字段酒馆基本不用。
- 只有目标前端明确要 V3 的新字段（`assets`、`nickname`、多语言说明等）时才出 V3。

### V2 外层结构

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "", "description": "", "personality": "", "scenario": "",
    "first_mes": "", "mes_example": "",
    "creator_notes": "", "system_prompt": "", "post_history_instructions": "",
    "alternate_greetings": [],
    "character_book": { "entries": [], "extensions": {} },
    "tags": [], "creator": "", "character_version": "",
    "extensions": {}
  }
}
```

- 外层可以另放一个 `name`，和 `data.name` 相同，用来兼容老程序；酒馆导入时以 `data.name` 为准。
- `character_book` 可以没有；有就必须是带 `entries` 数组的对象。
- 规范要求的字段即使为空也写空串或空数组，不省略。

V3 在此基础上把 `spec` / `spec_version` 改成 `chara_card_v3` / `3.0`，`data` 里多出：`assets`、`nickname`、`creator_notes_multilingual`、`source`、`group_only_greetings`（必填数组）、`creation_date`、`modification_date`（秒级时间戳）。

### 字段逐个说明

| 字段 | 干什么 | 进不进提示词、在哪 |
|---|---|---|
| `name` | 角色名，`{{char}}` 就是它 | 通过 `{{char}}` 出现在各处 |
| `description` | 本卡元提示词，写法见下方「description 写什么」 | 进。文本补全放在故事串的描述位；对话补全是提示词管理器里的「角色描述」条目 |
| `personality` | 性格摘要 | 进。位置同上，「角色性格」条目；可以留空，把性格写进 description |
| `scenario` | 当前场景、处境 | 进。聊天里可以单独覆盖 |
| `first_mes` | 首条开场白 | 不进系统部分，作为聊天的第一条 AI 消息显示，先过一遍作用于 AI 输出的正则 |
| `alternate_greetings` | 备选开场白 | 同上，是首条消息的左右滑切换。首条为空时，第一条备选顶上成为首条 |
| `mes_example` | 示例对话 | 本工作流不用，留空字符串。台词语料写进我们自己的角色设定，或放进世界书条目 |
| `system_prompt` | 角色专属系统提示 | 进，**替换**使用者自己的主提示词；空串时用使用者原来的。写 `{{original}}` 会在那里放回原来的主提示词 |
| `post_history_instructions` | 历史后指令 | 本工作流不写，留空。酒馆会把它放在聊天记录之后 |
| `creator_notes` | 给使用者看的说明 | 本工作流不写，留空。不进提示词，只在界面显示 |
| `tags` | 分类标签 | 本工作流不写，留 `[]` |
| `creator` / `character_version` | 作者、版本 | 不进 |
| `character_book` | 内嵌世界书 | 条目按自己的触发规则进；导入卡时酒馆会询问是否导入 |
| `extensions` | 各程序的扩展数据 | 必须是对象，默认 `{}`；不认识的键原样保留，不能删 |

`system_prompt` 要满足条件才替换：
- 文本补全：使用者开着「优先使用角色卡的系统提示」，默认是开的；
- 对话补全：提示词管理器里的「主提示词」条目没有勾「禁止覆盖」，也没有被禁用。

所以这个字段里只放「换一个预设也必须成立」的内容，不指望它一定生效。

#### description 写什么

- 以「你是……」开头，写本卡元提示词：AI 在这张卡里是谁、世界和眼下的处境、怎么扮演、不代写 {{user}}、文风要求。
- 精炼。角色设定、世界设定放世界书，不堆进这里。
- 只陈述现状，走向和结局留给场景。例：不写「若她说出喜欢，也会……」这类替未来下结论的句子。
- 如果玩家可以选择扮演任一方，身份写成作品的世界线，不写成其中某个角色。

#### extensions 里酒馆认的键

| 键 | 作用 |
|---|---|
| `depth_prompt` | 角色备注：`{ "prompt": "", "depth": 4, "role": "system" }`，按深度插进聊天记录里。深度默认 4，身份默认 `system`，可选 `user`、`assistant` |
| `talkativeness` | 群聊用，不用管，保持默认 0.5 |
| `fav` | 是否收藏，布尔值 |
| `world` | 绑定的外部世界书**名字**。导入卡不会顺带导入那本书，书要另外放进酒馆 |
| `regex_scripts` 等 | 其他扩展（正则、前端脚本等）存的数据，照原样保留 |

### 把现成内容装成可导入的卡

适用：作者手里是 txt / md / docx 形式的角色设定，或者已经分块写好的角色设定、文风规则、输出规范、开场白、世界书条目，要变成能拖进酒馆的 JSON 或 PNG。

1. **通读分块。** 把内容分成这几类：角色本身、当前场景、开场白、示例对话、文风规则、给 AI 的规则和输出要求、世界设定、给使用者看的说明、分不清的。已经分好块的，核对一遍每块属于哪类。
2. **按对照表放字段。**

   | 文档里的内容 | 放到 |
   |---|---|
   | 角色设定（外貌、性格、经历、说话方式） | `character_book` 的常驻条目 |
   | 已经写成一整块的角色设定（例如用 XML 标签包起来的一段） | 整块原样进一条常驻条目，不拆散 |
   | 写给 AI 的「你是……」总述 | `description`；文档里没有现成的，列出来问作者要不要写 |
   | 当前处境、故事开头的背景 | `scenario` |
   | 开场白（第一段、第二段……） | 第一段进 `first_mes`，其余按顺序进 `alternate_greetings` |
   | 对话示例、台词 | 跟角色设定放在同一条目里；量大时单独成条。`mes_example` 留空 |
   | 文风规则（叙事口吻、描写重点） | 常驻的世界书条目，插入深度靠近聊天末尾；只在特定场景用的文风做成触发条目，写明使用条件 |
   | 给 AI 的写作规则、输出格式 | 和总述一起进 `description`，或放 `system_prompt` |
   | 状态栏模版这类换了预设也必须生效的格式 | 低深度的世界书条目，或 `extensions.depth_prompt`；这两处不受预设开关影响 |
   | 世界设定、配角、地点（量大、只在提到时才需要） | `character_book` 的条目 |
   | 使用说明、作者的话、更新记录 | 不进卡，列出来交还作者 |
   | 作者名、版本号 | `creator` / `character_version`；标签不写 |

3. **只搬不改。** 转换时不润色、不删减、不合并；原文的错字和格式照留。放不下或归属不清的内容，列出来问作者，不自己决定。
4. **称呼不自动替换。** 原文里指代使用者的「你 / 玩家 / 主角名」、指代角色的名字，要不要换成 `{{user}}` / `{{char}}`，先问作者。
5. **用程序生成 JSON。** 用 JSON 序列化工具写出，不手拼字符串；换行交给序列化处理；文件存成不带 BOM 的 UTF-8。起手可以复制 `assets/card-v2-template.json`。
6. **跑校验脚本**，见「校验脚本」；有 ERROR 必须改完再交付。
7. **要 PNG 时**，用 `scripts/embed-png.ps1` 把这份 JSON 嵌进封面图，再对生成的 PNG 跑一次校验脚本。
8. **回读核对。** 从产出的 JSON 里取出 `first_mes` 和一段 `description`，与原文逐字比对；再核对开场白数量、世界书条目数和原文一致。

### 生成 PNG 卡

`scripts/embed-png.ps1`，只需要 Windows 自带的 PowerShell 5.1：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/embed-png.ps1 -Card .\某角色.json -Image .\封面.png -Out .\某角色.png
```

- 先把卡 JSON 做好并校验通过，再嵌图；脚本只检查 JSON 能解析、有 `data.name`，不替代校验脚本。
- 卡 JSON 原文先转 UTF-8 再转 base64，写进 `chara` 数据块，放在图片结尾块之前。封面里原有的 `chara` / `ccv3` 块先删掉，所以拿旧卡的 PNG 当封面也可以。
- 封面最好是 PNG：其余数据块一字节不动。JPG / BMP / GIF 会先转成 PNG，这一步会重新编码图片；WebP 读不了，先自己转格式。
- 默认只写 `chara`，酒馆能正常导入。加 `-WithV3` 时按酒馆自己导出的做法再写一份 `ccv3`，内容同卡，只把 `spec` / `spec_version` 改成 V3；没有 `spec` 的老格式卡不能加。
- 输出文件已存在时要加 `-Force` 才覆盖。
- 写完会回读一次，取出的卡数据与输入逐字相同才输出 `RESULT : PASS`；任何一步出错输出 `RESULT : FAIL`，退出码为 1。

### 校验脚本

`scripts/validate-card.ps1`，只需要 Windows 自带的 PowerShell 5.1：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/validate-card.ps1 -Path .\某角色.json
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/validate-card.ps1 -Path .\某角色.png
```

- 输入 `.json` 或 `.png`，PNG 会先取出 `ccv3` / `chara` 数据块（与酒馆同样的优先顺序）。
- **ERROR**：JSON 解析不了、`spec` 不认识、缺 `data` 或 `data.name`、字段类型不对、`extensions` 不是对象、`character_book` 没有 `entries` 数组、`depth_prompt` 的深度或身份不合法。
- **WARN**：有 BOM、缺规范要求的空字段、`alternate_greetings` 写成了字符串、`mes_example`、`creator_notes`、`post_history_instructions` 有内容或 `tags` 非空（本工作流不写这几个字段）、首条和备选开场白全空、外层 `name` 和 `data.name` 不一致、PNG 里两个数据块内容不同。
- 最后一行输出 `RESULT : PASS` 或 `RESULT : FAIL`，FAIL 时退出码为 1。
- 不检查 `character_book` 内部的条目配置。
