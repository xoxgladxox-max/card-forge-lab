# 配套（v3.9.0）

范围：世界和角色以外一张卡还需要的部分：文风、回复格式、开场白、装配导出。各部分独立，按需读对应一节。

总规则：

- 文风块骨架、状态栏字段、篇章生成器骨架都是示例。动笔前按这张卡提结构提案（用哪些块、记哪些状态、怎么排），作者确认后再写。例外：第五部分的卡文件格式是酒馆导入要求，照规范来。
- 只写偏离默认的项。模型本来就会做的不写。
- 同一条规则只放一处。放两处会改了一处忘了另一处，模型拿到两套打架的要求。
- 不代写 {{user}} 的台词、动作、心理、决定；不替 {{user}} 定剧情走向。
- 例子都标「例」。
- 表达精炼按 `cf-card-refine`：文风规则先立上位原则再落禁词和细节；标签只用圈内已验证的 tag，不造词；作者沟通里的比喻不进文风块；描写指导写「当 X 发生时着重写 Y 的前中后」，不写必然触发的剧本。

# 一、文风

AI 默认往训练分布的中间值靠：冲突浓度拉满、对话扁平、总结式抽象、碎句成行。文风块做四件事：把世界压回常态、把文风锚成坐标、把素材当参照物、只写偏离项。

## 宏观与微观

文风分两层，先写宏观，再写微观。

| 层 | 是什么 | 写什么 | 生效 |
|---|---|---|---|
| 宏观（基底文风） | 整张卡的上位方向 | 流派和读者定位、语体（口语或书面、直白程度）、叙事视角、镜头注视什么、节奏、全卡禁令 | 常驻 |
| 微观（特化文风、DLC 文风） | 某个区域、场景或模块的下位细节 | 启用条件、退出条件、该场景的感官素材、意象、命名习惯、句式味道 | 条件触发 |

- 微观服从宏观：只补充该场景独有的东西，不重写宏观已有的语体、视角和禁令。两层冲突时，在微观里写明「本模块内改为……」，否则以宏观为准。
- 微观必须写启用条件和退出条件，条件写成可判断的场景事实（地点、事件、在场者），不写「适当时」。
- 微观里的意象、词池和命名不往宏观渗：退出后立即退回宏观表面。
- 一张卡只有一个宏观；微观可以有多个，各自的启用条件不重叠，重叠时写明谁优先。
- 作者在某张卡里明确指定的单卡特例或硬禁令（例：禁某类服饰、锁定某种视角或称呼），按作用范围放进宏观 `全局禁令` 或对应微观模块，不写成所有卡通用的规则，精炼与审查时也不删改。

## 基准段落

宏观文风附一段样例正文，作为语感的直接参照。规则清单告诉模型不写什么，样例段让它看到要写成什么样。

- 一到两段，合计 200–500 字，标「例」。按宏观的全部要求写：语体、视角、镜头、节奏、对白习惯都要看得出来。
- 只写角色和环境，不写 {{user}} 的台词、动作、心理。
- 只作语感参照：样例段里的情节、意象和具体句子不在正文里复用（同查 S7 口癖复用）。
- 作者提供过喜欢的片段时，直接用那段并标明来源，不另写。
- 开场白是第二个校准点：它是模型最先读到的正文，按宏观的最高标准写，写完对照宏观逐条核对。开场白和样例段的语感要一致。

## 末尾放正文语态

模型倾向接着最后读到的文字往下写。离最新对话最近的注入如果是表格、状态栏模板或规则清单，正文容易写成报告腔或清单体。

- 同一个文风块里先写规则，样例段放最后。
- 必须贴近末尾的状态类信息（@Depth）写短，只写当前值，不写长规则；长规则放 ↑Char / ↓Char。
- 位置和深度的具体写法见 `cf-card-worldbook`「插入位置」。

## 镜头：推进剧情时看哪里

动笔前先问：这张卡推进剧情时，读者最想看到什么？镜头该停在哪些地方？答案来自出卡单的体验 key。

- 镜头规则写成条件：「当 X 时 → 注视 Y（限度：Z）；不是 X 时不展开 Y」。只写当镜头拉近时聚焦哪一部分，不预设剧情发展。
- 镜头焦距在「全景 ↔ 中距 ↔ 近距 ↔ 微观」四级之间双向推拉，由「感官聚焦（物理与动作维度）」与「情感聚焦（心理与话语维度）」两条独立维度构成：
  - 起点承接与按需选用：每轮起始镜头直接承接上一轮结束时的距离与状态（上一轮停在哪一级就从哪一级接续，不必每轮退回全景重头交代，也不必在单轮里凑齐四个镜头）。
  - 双向推拉与不跳级：镜头既可聚焦推进（远 → 近），也可拉远放大（近 → 远，如接触暂停、撤回或拉开距离时抽离回中距或全景）；每条轴在单轮回复里只停留在当前级深挖，或在相邻层级间平滑切换，不得无铺垫跨级快进。
  - 四级独立颗粒度（越远越宽泛，越近越详细）：全景、中距、近距、微观代表四档不同的描写颗粒度，停在哪一级就按哪一级的颗粒度展开：镜头越远越宽泛克制（只写空间剪影、步态、穿戴轮廓与远距声响，留白勾起画面联想），镜头越近越写实密集（才展开局部肌理、受力形变、体温湿度、气味与深入接触）。
  - 两轴各自按条件推进或回退：感官聚焦随空间距离与受力状态收窄或拉远；情感聚焦保持角色日常情感基底，在「场面话（表层日常话语）」与「心里话（深层真实意图）」之间切换，不随物理接触自动跳级，可同频递进也可错位反差。
- 涉及持续递进的特化或恋物文风，按四层结构组织：
  1. 第一层（顶层总控）：`镜头聚焦`（四级焦距双向推拉、起点承接与单轮推进限制、远宽近细四档颗粒度、感官与情感双轴独立、推进与留白条件）。
  2. 第二层（中层上位维度）：`感官聚焦` 与 `情感聚焦` 各自在全景、中距、近距、微观四级下的注视方向与限度（不含具体部位与具体反应）。
  3. 第三层（下位聚焦落点与机制）：承接第二层的四级，严格按「1. 全景 / 2. 中距 / 3. 近距 / 4. 微观」四档独立颗粒度（不两两合并）写出当前主题下每一级看什么：全景写远距声响与整体剪影钩子，中距写穿戴动作与局部轮廓，近距写贴身温度、气味与初步摩擦，微观写极致形变与深层接触。主干只写规律，具体动作、部位或生理反应一律放进 `(e.g., ...)` 并写明「实际发展按角色性格与实际情况进行推进」，防止模型死盯固定动作逐项打卡。
  4. 第四层（具体表现）：具象原子词池与按四级独立颗粒度一一对照的示例（放块末保持正文语态；纯控制推进节奏的模块可只保留四级示例而不设词池）。词池严禁写成闭合死名单，一律按「维度轴: e.g., 词1, 词2, ... etc.」写成开放的语感刻度，并注明「e.g. 仅标定颗粒度与尺度，优先根据现场材质、受力与动作派生更贴切的同类词，禁止把词库当必选填空题每轮打卡」。
- 条目拆分与灯色（顶层基底共用，下位专项按职责各自独立，互不混写）：
  - 常驻蓝灯（1 条，顶层共用）：放宏观底座 + 第一层 + 第二层。常驻里不出现具体部位与特化词池，日常走剧情时模型视野完全放开。
  - 条件绿灯（按独立职责拆块，1 个专项 1 条，不混写不同职责，也不按零件拆碎）：放该专项的第三层 + 第四层，由该主题的关键词或场景条件触发，共用同一个顶层蓝灯。
- 每张卡通常有三到五条场面镜头条件（例：交锋、日常、亲密、探索、对峙）。没有列出的场面按宏观的默认镜头；不是该场面时不展开（普通赶路不写人物身材，亲密场景不插入无关环境）。
- 凝视视角（男性向、女性向、中性）属于宏观，写在基底文风；它决定镜头在人物身上停多久、看哪里。

场面镜头例（自写，按当前卡改写）：

```yaml
镜头:
  交锋时: 注视双方的站位、出手前的身体预备动作和受力后的反应；不写旁观者。
  角色登场或换装时: 注视外形：身材、衣着材质、动作时衣物和身体的变化；其余时候不重复描写外形。
  亲密场景: 注视全感官和身心反应，强度逐步上升；不跳过铺垫。
  赶路和过场: 一两句交代时间和地点变化，镜头不停留。
```

四级双轴聚焦元提示词模板（自写，按「条目名作 key + 性质 / 分级 / 描写」格式写一二层）：

```yaml
镜头聚焦:
  性质: 叙事焦距随互动在「全景 ↔ 中距 ↔ 近距 ↔ 微观」四级之间双向推拉，过程重于结果；每轮直接承接上一轮结束时的镜头距离（不必每轮退回全景重头交代，也不必单轮凑齐四级），停留在当前级深挖或在相邻层级间平滑切换，不得跳过前戏或铺垫直接跨级。
  颗粒度: 四级对应四档独立颗粒度，镜头越远越宽泛克制（只写整体剪影、步态、轮廓与远距声响，留白勾起联想），镜头越近越写实密集（才展开局部肌理、受力形变、温湿度、气味与深层接触）。
  结构: 由「感官聚焦（物理与动作维度）」与「情感聚焦（心理与话语维度）」两条独立维度构成；两轴各自按条件推进或拉远，可同频递进，也可错位组合制造反差。
  推进与留白条件: 气氛或身体状态尚未立住时停留在当前级，可放慢、停顿、撤回或将镜头拉远；推进还是收回由角色当前意图、双方强弱关系与前序铺垫决定，不预设单一结局走向，但禁止无铺垫在单轮内走完从接触到结局的全流程。

感官聚焦:
  性质: 物理描写随空间距离与受力状态在四级颗粒度间缩放，从远距声影与整体轮廓逐步收窄到局部形变，或随撤开拉远退回整体姿态；身体反应与话语态度可以不同步。
  分级:
    - 全景（远距或日常过场时） → 注视整体身形剪影、穿戴轮廓、站位落差、步态和远距传来的声响（限度：宽泛点染勾起联想，不写局部细节）
    - 中距（视线停留或蓄力动作时） → 注视局部张力与穿戴动作：受力处的绷紧、衣物与身体的挤压轮廓、动作带动的力量传导（限度：通过可见轮廓表现张力，不直接跳入深层接触）
    - 近距（距离拉近或初步接触时） → 加入贴身才能感到的重量、温度、湿度、气味与摩擦声，以及接触撤开瞬间的余温空白（限度：保留双方反应与拉扯空间，不直接跳入全面压制）
    - 微观（全面压制或深度接触时） → 多种感官同时交织：力量在身体各处的连续传导、挤压形变、液体与声响（动作分开或撤退时，随镜头拉远退回中近距或全景）
  描写: 每次聚焦变化时，着重写动作开始前的蓄力轮廓、动作当中的受力形变、动作停下或撤走后的留痕与余韵。

情感聚焦:
  性质: 语言与独白保持角色日常的情感基底，在「场面话（表层日常态度）」与「心里话（深层真实意图）」之间按心理防线独立切换；不预设发展，不随物理接触自动跳级。
  分级:
    - 全景（日常互动或保持距离感时） → 维持角色日常的场面话与表层态度；即使物理上已发生接触，台词仍可保持平淡克制（限度：真实波动只留在内心独白或细微停顿里）
    - 中距（暗中试探或掩饰真实意图时） → 场面话夹带潜台词：嘴上用日常理由掩护动作，用停顿或提问试探对方；独白捕捉双方破绽（限度：点出状态而不直接挑明底牌）
    - 近距（优势确立或防线松动时） → 场面话开始撑不住：日常借口失效，转为引导、追问、命令或嘴硬下的退让，直接谈论当下的身体反应
    - 微观（情绪压过克制或不再掩饰真实意图时） → 心里的话不再遮掩：抛开场面话，内心独白与直白对白说出同一种真实感受，直接写当下的感受与冲动（结束后退回角色日常话语）
  描写: 着重写开口前的停顿、嘴上态度与身体状态的一致或反差，以及从场面话滑向心里话的转折瞬间；不替对方做决定。
```

## 世界分层

| 层 | 占比 | 内容 |
|---|---|---|
| 第三层 突发冲突与暗线 | 约 10% | 特定角色的暗手、危机引爆；只是局部引爆点，不是世界底层规则 |
| 第二层 题材特异载体 | | 该世界特有的媒介、制度、技术；对里面的人是理所当然 |
| 第一层 基底秩序 | 约 90% | 可信的日常：语言、作息、空间、物件 |

- 常态先立住。90% 不扎实，10% 的破坏就没有痛感。
- 第二层是日常工具，不是奇观：虚拟配信、魔法、机甲，对角色来说就是书包里的手机。
- 某个角色的手段（录音、社死威胁、操控人心）不泛化成全员高压、人人勾心斗角。
- 检查：连续写三场日常戏（上学、社团、吃饭），任何一场必须靠冲突才成立，就是常态没立住。

## 文风坐标

不用「有质感」「文艺」「高级感」这类词定文风。

1. 命名锚定：具体作家、作品、流派。例：日系青春群像 → 武田绫乃《吹响！上低音号》、绫奈由仁子《It's MyGO!!!!!》；硬汉派 → 钱德勒《漫长的告别》；中式古典白话 → 张爱玲、白先勇。
2. 提炼可操作特征：每条是可执行、可检查的动作或结构。例：群体中视线交错与话没说完的停顿、动作时的肌肉与呼吸细节、台词只露水面、环境光影与情绪融合。
3. 负面排除：每种文风列一到两条禁止写法，用刚性动词。例：日系青春群像严禁电报体短句成行（「停了一下。又停了一下。笑了笑。」）。

例（「停下 + 观察 + 暗笑」）：

- ❌ 她停下了。/ 她看着手机。/ 嘴角扬起。/ 很可怕。
- ✅ 换气扇规律的嗡鸣把两人之间的空白拖得很长。她的指尖在亮起的屏幕上轻轻一滑，视线越过谱架边缘扫过来，右嘴角那颗细小的痣随着浅淡的笑意微微上提。

## 外语素材

外语台词、口癖、拟声、方言是语感节奏与心理密度的参照物，不是待翻译的源文本。

1. 识别功能：这句在场景里承担什么（压迫、拉近、反差、仪式感）。
2. 理解密度：轻飘飘的撒娇，还是坠着寒意的宣判。
3. 用目标语言的句式节律、语气词、神态动作重造等价效果，不字对字翻。
4. 必要时在设定里保留原语关键短语作锚点（如 `ゲス顔`）。

- 不音译拟声（「库库库」「阿哈」），换成喉音、气声、呼吸停顿或嘴角肌肉的白描。
- 不字面直译丢节奏。

可迁移技巧（例，按卡调整）：

- 一人称双轨：表演态（撒娇、装无辜、营业）自称名字或昵称，真心态（逼问、宣示、撕开伪装）切换为「我」。
- 设问出题式推进：提问 → 公布答案 → 答案即攻击 → 逼对方表态 → 沉默当作同意。掌控感从句式里出来，不用旁白解释。

## 写文风块

- 只写偏离通用认知的特异规则；AI 已掌握的常识写多了是噪音，稀释权重。
- 用对应圈子（Pixiv / 日推 / 中文二创 / 英文 fandom）已验证的高密度标签唤醒语料。标签和维度写在那张卡自己的文风设定里，不写在本技能。
- 给维度不给路径：定义两极坐标（表演态 vs 真心态、掌控端 vs 臣服端），不锁死具体动作与固定情节；列出的部位、道具、动作、台词只是可能性之一。
- 奖赏稀缺：夸奖、温柔、甜头在权力互动里是受控的稀缺筹码，越吝啬，给出时冲击越强。
- 每个规则块问一句：它服务于哪个体验锚点？不服务任何锚点的删。
- 视角：第三人称受限视角，镜头只聚焦现场，不替 {{user}} 写动作、心理、决定；角色的里人格只在死角、独处、背对他人时浮现，人前维持表层。
- 红线与边界用「严禁」；可能性空间用「可以」「倾向」「重点放在」。

骨架（例）：

```xml
<style name="[文风名]">
[启用条件和退出条件。基底文风常驻可省，特化 / DLC 文风必写]

本块为可能性空间，不是任务清单。按实际剧情与角色性格自适应，示例仅供参考，禁止照抄固定句式。

## 标签锚定
[真实圈子标签，按题材]

## 核心倾向
[本风格最在意的感觉、落差、权力关系或节拍，两到四条]

## 镜头
[当 X 时 → 注视 Y；不是 X 时不展开。基底文风写全卡主要场面，特化文风只写本场景与基底不同的地方]

## 感官与词池
[五感各给一组注意力去向：摸得到的 / 闻得到的 / 尝得到的 / 听得到的 / 身体内部的。写部位与物理属性，不写主观感受词。特化 / DLC 文风可按材质、光泽、动态、温度、湿度、气味、声音列具象质感词池，供连续描写轮换调用、避免复读同一词]

  [维度 2]：……
  [特化文风有多个不同动作、部位或互动切面时，可按切面各给一段短示例；每段对应不同切面，不写同构重复段落]

## 描写重点
- [两到四条，本块独有的]

## 元原则
- 可能性空间声明、成年限定、激活边界（特化文风）
- 全局禁令不在这里重复，只写本块专属的

## 样例段
[基底文风必写，放最后；特化文风可省。写法见「基准段落」]
</style>
```

默认整块一条。只有满足第四部分第 3 条三明治护栏时才拆：「标签锚定 / 核心倾向 / 感官」进头，「描写指导」各维度拆成子项，「描写重点 / 元原则」进尾。

输出三层：正文（沉浸式叙事，不可省）→ 条件触发块（只在剧情涉及直播、舆论、录音等媒介事件时出现）→ 状态栏（回复末尾，代码块展示场景、表里状态、关系指标、在场道具；数值变动带正文因果）。

自检：

- 当前场景有 90% 常态质感吗？有没有全员高压？
- 用具体作家、作品、流派锚定了吗？列了禁止项吗？
- 段落舒展吗？碎句成行清了吗？动作融进环境与心理了吗？
- 外语素材等价重造了吗？音译和直译清了吗？
- 压迫感通过对方视角与微动作侧写呈现了吗？表里反差有人称分工和隐秘性撑着吗？
- 还有 AI 默认常识的冗余吗？每条规则服务哪个体验锚点？
- 宏观和微观分开了吗？微观有可判断的启用和退出条件吗？有没有重写宏观已有的内容？
- 镜头是否在「全景 ↔ 中距 ↔ 近距 ↔ 微观」四级之间支持双向推拉、承接上轮起点（不强求单轮写满四级），并保持远宽近细四档独立颗粒度与双轴独立、不跳级？
- 一二层是否作为常驻蓝灯保持纯上位（不含具体部位），不同职责的下位专项是否拆成各自独立的条件绿灯（不混写进同一条）？
- 第三层是否严格按「全景 / 中距 / 近距 / 微观」四档独立颗粒度（不两两合并）写出规律并用 `(e.g., ... 实际发展按角色性格与实际情况进行推进)` 避免打卡，第四层词池是否用 `e.g., ... etc.` 写成开放的语感刻度並附四级对照示例？
- 镜头写成「当 X → 注视 Y」了吗？不是该场面时镜头有没有继续停在 Y 上？
- 宏观附了样例段吗？样例段和开场白语感一致吗？离末尾最近的注入是正文语态还是表格和规则？

# 二、回复格式与状态栏

范围：AI 每轮回复的形状：由哪几块组成、怎么收尾、要不要思维链、状态栏记什么、人称和语言。角色、世界、文风不在这里。

先问作者，没定的不替作者定：

1. 每轮回复由哪几块组成，按顺序列。例：正文 → 状态栏；思维链 → 正文 → 状态栏。
2. 要不要状态栏；要的话记哪些状态。
3. 要不要思维链；要的话给不给使用者看。
4. 叙述人称和视角（例：第二人称写 {{user}}、第三人称写角色）。
5. 正文语言、对白格式、需要保留原文的专有名词。

## 放在卡的哪里

| 位置 | 特点 | 放 |
|---|---|---|
| `description` | 与本卡元提示词一起，每轮都带 | 最核心的几条：不代写 {{user}}、停在哪里、叙述人称 |
| `system_prompt` | 替换使用者的主提示词；可能被预设挡住 | 完整输出规范 |
| 低深度世界书条目、`depth_prompt` | 不受预设开关影响，按深度插进聊天记录 | 换了预设也必须生效的格式，例如状态栏模版 |

本工作流不写 `post_history_instructions`。

## 回复结构

- 各块按固定顺序出现，每块有明确的开头和结尾标记（例：状态栏用一对 XML 标签包起来），方便正则隐藏或美化。
- 收尾停在交给 {{user}} 的地方：角色这一轮说完、做完就停。
- 长度给范围，不给最低字数；最低字数逼模型灌水、复读。
- 不在规则里预写剧情走向（「这一轮推进到某某事件」是剧情安排，不是格式）。

## 思维链

- 只在需要时加：状态多、需要回合间核对的卡；或模型容易写偏、需要先对照规则的卡。模型自带推理时一般不加。
- 写成核对步骤，不写成剧情草稿。例：核对 {{user}} 这轮做了什么、哪些状态要变、有没有越过角色边界。
- 三到五步，只列要核对的项，不列答案。
- 用固定标签包起来（例：`<thinking>…</thinking>`），配正则从显示或后续上下文里去掉；否则占上下文，模型还会模仿上一轮的思考。

## 状态栏

- 只记跨回合要保持、或本轮确实变了的状态：日期、时间、地点、服装变化、持有物、伤势、关系变量。静态外貌、没变的衣物、正文能直接看出的心理不进。
- 字段规则写「记什么、什么时候变」，不塞正文描写、情绪结论或固定剧情流程。
- 状态没变时允许沿用、简写或省略。
- 好感度、信任度只表示当前状态，变化要有事件依据；数值高低不等于唯一的心理或剧情走向。
- 不为了「像游戏」加字段。
- 有开场白时，开场白末尾带一份初始状态栏，格式与模版完全一致。
- MVU（脚本把状态存成变量、每轮由模型输出更新语句）同理：只建跨回合要用的变量，只记当前值，变化有事件依据。

## 语言

- 写明叙述人称、视角、正文语言；保留原文的专有名词列清单。
- 对白、动作、心理的区分格式（引号、星号、括号）选一种，全卡统一。
- 只写和默认不同的地方，一条一句。

交付前：

- [ ] 「先问作者」各项都有答复。
- [ ] 每条规则只在一个位置。
- [ ] 没有最低字数，没有预写剧情。
- [ ] 收尾规则写明不代写 {{user}}。
- [ ] 状态栏每个字段说得出为什么跨回合记。

缺口：

- MVU 技术接入（脚本、初始化文件、更新语法、配套正则）未整理核实。
- 小白X（LittleWhiteBox 扩展）的接入方式未调研。
- 思维链对不同模型的实际效果没有实测记录。

# 三、开场白

## 酒馆里的实际行为

- `first_mes` 是首条；`alternate_greetings` 每条是首条的左右滑切换，滑到哪条就从哪条开局。`first_mes` 为空时第一条备选顶上。
- 开场白显示前会先过作用于 AI 输出的正则，状态栏这类块在开场白里也会被隐藏或美化。
- 开场白之后是聊天记录的一部分，模型照着它的长度、人称、格式和口吻往下写。开场白是回复格式的第一个样板。

先定：

1. 开几条：首条一条，备选几条。
2. 每条什么开局：时间、地点、两人此刻的关系位置。
3. 叙述人称、视角、正文语言、对白格式；卡里有规定照用，没有先问作者。
4. 有没有状态栏、初始值是什么。
5. 首条要不要写成篇章生成器。

## 一条开场白写什么

- 场景：在哪、什么时候、周围有什么，写到 {{user}} 知道自己站在哪里就够。
- 角色此刻在做什么：用动作和台词表现，不写人物介绍。
- 停在需要 {{user}} 回应的时刻（例：一句问话、一个递过来的东西、刚发生还没处理的事；换成当前场景里的东西）。停下后不补氛围收尾或引导句。
- 有状态栏时末尾放初始状态栏，格式与模版一字不差。

不写：

- {{user}} 的台词、动作、心理、决定；{{user}} 最多是在场。
- 剧情走向：开场白给局面，不给结局或下一步安排。
- 人物介绍、世界观讲解：开场白只演一场戏。
- XML 包裹：包裹会被模型学进正文。

## 前提要有出处

处境、起因、身体状态、时间压力，每条都要在原作或已确认设定里找到出处。

- 找得到：照写。
- 找不到：改成开放写法，只写现象，不定死原因。例：写「送来得比平常晚」，不写「断供了」。
- 为营造气氛编出来的前提，常和人设相反，还会替 {{user}} 定死走向。这是开场白最常见的错。

## 用原文开场

- 原作有合适场面时优先用原文，照原作句式和节奏，不改写成缩写或平铺旁白。
- 标「原文」必须逐字对得上：用脚本从料源文件按起止句截取，写入后核对；核对不过不许标原文。
- 停在原文的自然停点，不续写。
- 原作没有对应段落、只能自写的，照原文风格写，并在节点里标明自写。

## 首条与备选

- 首条放最能代表这张卡、大多数人会玩的开局。
- 备选各开一个不同局面：不同时间点、地点、关系阶段、事件起点。只改几句措辞的备选没有意义。
- 每条单独成立，不依赖看过首条，不互相引用。
- 各条人称、格式、状态栏模版一致，长度相近；某条特别长，从那条开局的聊天也会变长。

## 篇章生成器

- 卡有两条以上不同开局，或玩家可以选扮演哪一方时，`first_mes` 写成篇章生成器：一段原文引子加一个 yaml 选择器，让玩家选开局和视角。
- 结构、选择器写法、骨架和配套要求见 `references/generator-template.md`（示例，按卡调整）。
- 用了生成器，首条的要求（代表性开局、末尾状态栏、回复格式样板）改由第一条备选和玩家选完后的第一场承担。

## 称呼与宏

- 使用者用 `{{user}}`，角色用 `{{char}}` 或角色名，全卡统一。
- 不用来源不明的宏；`{{random}}` 这类非核心宏先确认目标环境支持。

交付前：

- [ ] 每条每个前提说得出出处，说不出的已改开放写法。
- [ ] 没有一句替 {{user}} 说话、行动或做决定。
- [ ] 每条停在需要 {{user}} 回应的时刻，后面没有收尾或引导句。
- [ ] 标「原文」的都用脚本核对过。
- [ ] 备选开局各不相同，每条单独成立。
- [ ] 人称、格式、状态栏模版与卡的规定一致。
- [ ] 用了篇章生成器的：选择栏留空，篇章与备选一一对应，代码块后没有收尾句，输出规范里有接续那一句。

# 四、装配：内容放进卡的哪里

1. 一节点一条目。
   - `world_book/**/<条目>.md` 正文 = 条目 content，元信息头 = 触发配置。
   - `greeting` 放 `message/<n>.md`：`0.md` 为 `first_mes`，`1.md` 起为 `alternate_greetings`。
   - 单槽字段放顶层 `<字段>.md`（`description.md`、`system_prompt.md` 等，空字段不生成）。`note` 不导出。creator_notes、post_history_instructions、tags、mes_example 默认不写。
   - 一个节点要出多条条目时（例：配角群每人一条），每人一个 `.md` 放 `world_book/character/`（或 `world_book/`）下；不在导出后另跑脚本拆，否则构建记录的指纹对不上。
   - 进世界书的 character 节点放 `world_book/` 下（或显式写 `target: character_book`）；`description.md` 由 output 节点写本卡元提示词。corpus、output、greeting 写明去处或按规定目录放。
2. 层级对应注入深度：世界观与社会规律 @D4 → 机制与冲突规则 @D3 → 角色与剧情 @D2 → 文风 @D1 → 输出规范 @D0。深度写在节点元信息头，导出时照搬。
3. 三明治可选，默认每条自包含。要用时（例：多条模块共用一个总纲框），开头、收尾各建一个节点放同一父目录，头字段写 `wrap: head` / `wrap: tail`，并满足：首尾常驻、`ignore_budget: true`、与组内条目同一 position 与深度、开头 order 组内最小、收尾最大。不满足时酒馆会拆散首尾（超预算先丢开头、位置不同拼不到一起）。护栏齐全也挡不住用户自己挂的全局条目插进中间。
4. 条目要能单独看懂：单独成条的内容都有带名字的顶层包裹，包裹里的 YAML 顶格写；元信息头写 `title`（酒馆世界书列表里的标题）。交付前按酒馆里看到的样子逐条过一遍标题、包裹首行和尾行。
   - 标签名按节点类型取固定英文小写词，不带作品名或人物名；名字写进 `name`，是这个人的哪一部分写进 `part`。同类多条靠 name 分清。包裹内部不再套标签；配角群每块各自成对。输出侧标签（状态栏、思维链）由输出规范自己定。
   - title 用最短自然叫法，不写路径，全卡不重复。只有不加范围分不清时才加（例：时间线分原作基底和 IF 分支两条，分支那条写「某分支世界时间线」）；其余不加范围词（例：晚钟镇、钟楼、小满、小满口癖语料）。通用名（时间线、历史、势力格局、魔法体系）单看认不出是哪一层，要加所属层的范围词。title 不要求复述 `name` / `part` 全称。

   | 节点类型 | 包裹 | title 例（照本卡改写） |
   |---|---|---|
   | world / location / lore / rule / item | `<world name="…">`，其余同形，标签名即类型名 | 晚钟镇世界观（顶层）、晚钟镇世界时间线 |
   | character | `<character name="人物名">` | 小满 |
   | module / corpus | `<character name="人物名" part="模块名">` | 小满口癖语料 |
   | 配角群（一条多人） | 每人一个 `<character name="…">` | 配角群 |
   | style | `<style name="文风名">` | 雨季文风 |
   | plot（剧情） | `<plot name="…">` | 出罐与初见 |
   | wiki（设定百科） | `<lore name="…">`（沿用 lore 标签） | 16Lab |
   | event（事件） | `<event name="…">` | 物资被截 |
   | output | 进 description 不加包裹；进世界书用 `<output>` | 输出规范 |
   | greeting | 不加包裹 | — |

5. 校验分两个跑：卡本体字段与 JSON / PNG 载体按第五部分，跑 `scripts/validate-card.ps1`；世界书条目（触发、位置枚举、递归）跑 `scripts/validate-worldbook.ps1`。
6. 排序：按组连续编号不重复：世界（world / location / lore / rule / item）1xx → 人物（character / module / corpus）2xx → 文风 3xx → 输出 4xx → 开场白及其他（greeting / plot / event / wiki）5xx；不穿插。
   - check 只看 type 不看内容；报「格式适配提醒」时按内容确认 type，再适配标签和 order。
   - 组内按节点树先父后子，父子挨在一起。节点不写 order，由导出工具编；一组超过 99 条时全卡改四位编号（1001 起）。
   - 超预算时酒馆先保留 order 大的，世界组最先被挤掉；大世界书里关键的世界条目设 `ignore_budget: true`。

# 五、装配：卡文件格式

范围：卡 JSON 对象的外层：字段、作用、装配、PNG、校验。不管内容质量，也不管 `character_book` 内部条目配置（只保证它是带 `entries` 数组的对象）。

## 三种载体

| 载体 | 怎么存 | 酒馆的行为 |
|---|---|---|
| `.json` | 文件就是卡对象，UTF-8 无 BOM | 有 `spec` 按 V2/V3 读 `data`；无 `spec` 有 `name` 按 V1 读；还认 Pygmalion 的 `char_name` |
| `.png` | tEXt 数据块，关键字 `chara`（V2）或 `ccv3`（V3），值是卡 JSON → UTF-8 → base64 | 读取时 `ccv3` 优先；酒馆导出 PNG 时两块都写，`ccv3` 那份只改 `spec` / `spec_version` |
| `.charx` | V3 zip 包，根目录 `card.json`，素材在 `assets/` | 酒馆能导入；本技能只认识，不产出 |

改 PNG 卡只替换 `chara` / `ccv3` 两块，其余数据块一字节不动，图片不重编码；用 `scripts/embed-png.ps1`。

## V2 / V3

- 默认 V2：酒馆内部按 V2 存卡，V3 导入后也按 `data` 读，V3 新字段酒馆基本不用。
- 目标前端明确要 V3 新字段（`assets`、`nickname`、多语言说明等）时才出 V3。

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "", "description": "", "personality": "", "scenario": "",
    "first_mes": "", "mes_example": "",
    "creator_notes": "", "system_prompt": "", "post_history_instructions": "",
    "alternate_greetings": [],
    "character_book": { "entries": [], "extensions": {} },
    "tags": [], "creator": "", "character_version": "",
    "extensions": {}
  }
}
```

- 外层可另放一个与 `data.name` 相同的 `name` 兼容老程序；酒馆以 `data.name` 为准。
- `character_book` 可以没有；有就必须是带 `entries` 数组的对象。
- 规范要求的字段为空也写空串或空数组，不省略。
- V3：`spec` / `spec_version` 改为 `chara_card_v3` / `3.0`；`data` 多出 `assets`、`nickname`、`creator_notes_multilingual`、`source`、`group_only_greetings`（必填数组）、`creation_date`、`modification_date`（秒级时间戳）。

## 字段

| 字段 | 作用 | 进不进提示词 |
|---|---|---|
| `name` | 角色名，即 `{{char}}` | 通过 `{{char}}` 出现 |
| `description` | 本卡元提示词 | 进。文本补全在描述位；对话补全是提示词管理器的「角色描述」条目 |
| `personality` | 性格摘要 | 进，「角色性格」条目；可留空，写进 description |
| `scenario` | 当前场景、处境 | 进；聊天里可单独覆盖 |
| `first_mes` | 首条开场白 | 作为第一条 AI 消息显示，先过 AI 输出正则 |
| `alternate_greetings` | 备选开场白 | 同上，左右滑切换 |
| `mes_example` | 示例对话 | 本工作流不用，留空。台词写进角色设定或世界书条目 |
| `system_prompt` | 角色专属系统提示 | 进，替换使用者的主提示词；空串时用原来的；写 `{{original}}` 放回原主提示词 |
| `post_history_instructions` | 历史后指令 | 本工作流不写，留空 |
| `creator_notes` | 给使用者看的说明 | 本工作流不写，留空；不进提示词 |
| `tags` | 分类标签 | 本工作流不写，留 `[]` |
| `creator` / `character_version` | 作者、版本 | 不进 |
| `character_book` | 内嵌世界书 | 条目按自己的触发规则进；导入时酒馆询问是否导入 |
| `extensions` | 各程序扩展数据 | 必须是对象，默认 `{}`；不认识的键原样保留 |

`system_prompt` 生效条件：文本补全开着「优先使用角色卡的系统提示」（默认开）；对话补全的「主提示词」条目没勾「禁止覆盖」也没被禁用。所以只放换预设也必须成立的内容，不指望一定生效。

description 写什么：

- 以「你是……」开头：AI 在这张卡里是谁、世界和眼下处境、怎么扮演、不代写 {{user}}、文风要求。
- 精炼；角色和世界设定放世界书。
- 只陈述现状，不替未来下结论（例：不写「若她说出喜欢，也会……」）。
- 玩家可选扮演任一方时，身份写成作品的世界线，不写成某个角色。

extensions 里酒馆认的键：

| 键 | 作用 |
|---|---|
| `depth_prompt` | 角色备注 `{ "prompt": "", "depth": 4, "role": "system" }`，按深度插进聊天记录；role 可选 `user`、`assistant` |
| `talkativeness` | 群聊用，保持默认 0.5 |
| `fav` | 是否收藏，布尔值 |
| `world` | 绑定外部世界书的名字；导入卡不会顺带导入那本书 |
| `regex_scripts` 等 | 其他扩展数据，原样保留 |

## 文档转卡

适用：作者手里是 txt / md / docx，或已分块写好的设定、文风、输出规范、开场白、世界书条目，要变成能导入的 JSON 或 PNG。

1. 通读分块：角色本身、当前场景、开场白、示例对话、文风规则、给 AI 的规则与输出要求、世界设定、给使用者看的说明、分不清的。已分好块的核对归类。
2. 按对照表放字段：

   | 内容 | 放到 |
   |---|---|
   | 角色设定（外貌、性格、经历、说话方式） | `character_book` 常驻条目 |
   | 已写成一整块的角色设定（例：XML 包起来的一段） | 整块原样进一条常驻条目，不拆 |
   | 写给 AI 的「你是……」总述 | `description`；没有现成的，列出来问作者要不要写 |
   | 当前处境、故事开头背景 | `scenario` |
   | 开场白 | 第一段进 `first_mes`，其余按顺序进 `alternate_greetings` |
   | 对话示例、台词 | 与角色设定同一条目；量大单独成条。`mes_example` 留空 |
   | 文风规则 | 常驻条目，深度靠近聊天末尾；只在特定场景用的做成触发条目，写明使用条件 |
   | 给 AI 的写作规则、输出格式 | 与总述一起进 `description`，或放 `system_prompt` |
   | 换预设也必须生效的格式（状态栏模版） | 低深度条目或 `extensions.depth_prompt` |
   | 世界设定、配角、地点（量大、提到才需要） | `character_book` 条目 |
   | 使用说明、作者附言、更新记录 | 不进卡，列出来交还作者 |
   | 作者名、版本号 | `creator` / `character_version`；标签不写 |

3. 只搬不改：不润色、不删减、不合并，错字和格式照留。放不下或归属不清的列出来问作者。
4. 称呼不自动替换：原文的「你 / 玩家 / 主角名」和角色名要不要换成 `{{user}}` / `{{char}}`，先问作者。
5. 用程序生成 JSON：序列化工具写出，不手拼字符串；存 UTF-8 无 BOM。起手可复制 `assets/card-v2-template.json`。
6. 跑校验脚本，有 ERROR 改完再交付。
7. 要 PNG 时用 `scripts/embed-png.ps1` 嵌进封面图，再对 PNG 跑一次校验。
8. 回读核对：取 `first_mes` 和一段 `description` 与原文逐字比对；核对开场白数量、条目数与原文一致。

## 生成 PNG

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/embed-png.ps1 -Card .\某角色.json -Image .\封面.png -Out .\某角色.png
```

- 只需 Windows 自带 PowerShell 5.1。先做好 JSON 并校验通过再嵌图；脚本只查 JSON 能解析、有 `data.name`。
- 写进 `chara` 块，放在图片结尾块之前；封面原有的 `chara` / `ccv3` 先删掉，旧卡 PNG 可当封面。
- 封面最好是 PNG（其余块不动）；JPG / BMP / GIF 会先转 PNG 并重编码；WebP 读不了，先自己转。
- 默认只写 `chara`。加 `-WithV3` 再写一份 `ccv3`（只改 `spec` / `spec_version`）；没有 `spec` 的老格式卡不能加。
- 输出已存在时加 `-Force` 才覆盖。
- 写完回读，卡数据与输入逐字相同才输出 `RESULT : PASS`；出错输出 `RESULT : FAIL`，退出码 1。

## 校验脚本

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/validate-card.ps1 -Path .\某角色.json
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/validate-card.ps1 -Path .\某角色.png
```

- PNG 先取 `ccv3` / `chara`（与酒馆同样优先顺序）。
- ERROR：JSON 解析不了、`spec` 不认识、缺 `data` 或 `data.name`、字段类型不对、`extensions` 不是对象、`character_book` 没有 `entries` 数组、`depth_prompt` 深度或身份不合法。
- WARN：有 BOM、缺规范要求的空字段、`alternate_greetings` 写成字符串、`mes_example` / `creator_notes` / `post_history_instructions` 有内容或 `tags` 非空、首条和备选全空、外层 `name` 与 `data.name` 不一致、PNG 两个数据块内容不同。
- 最后一行 `RESULT : PASS` 或 `RESULT : FAIL`，FAIL 退出码 1。不查 `character_book` 内部条目。
