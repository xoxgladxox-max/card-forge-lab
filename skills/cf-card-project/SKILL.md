# 卡工程流程

本技能不依赖具体工具：流程里只写要做什么、怎么核对，拆卡、装卡、推送、拉回用的命令见文末「工具对照」。标【待定】的项还没有作者决定，执行到那里按写明的默认做法处理，并在报告里列出。

## 一、三样东西各管什么

| 东西 | 是什么 | 管什么 |
|---|---|---|
| 工作台 | 你正在用的编辑器或 AI 工具，以及制卡技能 | 查资料、提方案、改内容。产物在作者确认前都是候选 |
| 卡工程 | 一张卡的文件夹 | 唯一正式落档的地方。写进卡工程才算数 |
| 同步工具 | 卡工程和酒馆之间的拆卡、装卡、推送、拉回工具 | 两边双向同步 |

工作台的产物不直接写进卡工程的正式文件；酒馆里的改动也不直接覆盖正式文件。两个方向都先进 `候选\` 或 `待归位\`，作者确认后才写进去。

## 二、位置和命名

```
<卡工程根目录>\<卡名>\
```

- **一张卡一个文件夹**：直接放在卡工程根目录下，不设作品层。卡名是酒馆里卡文件的名字去掉 `.png`。例：酒馆里是 `示例卡.png`，卡工程就叫 `示例卡`。推送和拉回靠卡文件名找酒馆里的卡，两者相同就不会推错卡。
- **放在工作台能写入的位置**：有的工具只允许写当前工作区目录，跨盘或通过目录连接写入会被拒绝。被拒绝时停下报告，不用 shell 绕过限制写卡工程。
- **资料可以在别处**：其他位置的资料只读，正文里写资料路径即可，不复制进卡工程。
- **改名**：酒馆里的卡改名后，卡工程目录同步改名。条目 id 不变。
- 名字里有 `[ ]` 时，PowerShell 里一律用 `-LiteralPath`。

## 三、卡工程里的分区

```
<卡名>\
  card.md                      卡根：卡名、世界书名、留在卡里的扩展设置
  <字段>.md                    单槽字段（description.md、system_prompt.md 等），空字段不生成
  message\0.md                 开场白（0.md 为 first_mes，1.md 起为 alternate_greetings）
  world_book\**\<条目>.md      世界书条目，可按角色/世界/文风建子目录分组
  regex\<序号>-<名>.json+.html 拆出的正则设置与替换内容
  scripts\<序号>-<名>.json+.js 拆出的酒馆助手脚本、variables.json、xiaobaix-tasks.json
  character.png                角色卡封面图
  记录\                        决策记录、出卡单、对应表、核对结果
  候选\                        工作台产物和有分歧的版本，等作者确认
  待归位\                      拉回时酒馆里改了、需要作者处理的内容（工具自动写）
  backups\                     推送、拉回、装卡前的自动备份（工具自动写）
  dist\                        装出来的成品（工具自动写）
```

**装卡只认规定位置的文件**：`card.md`、顶层单槽字段 `.md`、`message\<n>.md`、`world_book\**\*.md`、`regex\`、`scripts\`、`character.png`。`调研.md`、`记录\`、`候选\`、`待归位\`、`note\`、`backups\`、`dist\` 均不进卡。

- 候选写成 `候选\<条目名>\<来源>.md`，例如 `候选\示例角色\旧节点.md`、`候选\示例角色\酒馆版.md`。
- **世界书条目文件**：一条世界书条目一个 `.md`，可以按类型分子目录（如 `world_book\world\`、`world_book\character\`），也可以平铺；子目录只用于分组，装卡以文件开头的设置为准。

## 四、认文件、认版本的规则

| 要判断什么 | 用什么判断 |
|---|---|
| 这是哪一条 | 名字和 id。id（如 `wb-2`）不随改名变化 |
| 是不是同一版 | 正文哈希，由程序算 |
| 差在哪里 | 只有哈希不同时才看，只看程序列出的差异行 |
| 有多少、对不对得上 | 由程序给出数字，不靠自己数 |

- 名字相同不代表内容相同。常见情况：酒馆里的卡和一份旧导出 JSON 有几条条目名字完全一样，正文却不同。只比描述和条目数量就会误判成同一版。
- 每一项都比，不抽查。
- 比对之前，先把程序实际拿去比较的内容打印出几行，确认比的是正文本身，不是夹带了说明块或开头设置。
- 大文件分段读，每段注明起止行号，读完核对总行数。读取结果被截断时，接着读后面的部分，不当作读完。
- 判断哪边更新时看修改时间，但不自动选边，列出来交作者决定。

## 五、流程

### A. 接卡：把酒馆里的卡变成卡工程

1. 确认卡文件名：在酒馆数据目录 `characters\` 下找到这张卡的 PNG，或用同步工具列出当前卡。
2. 卡工程目录先不建；拆卡工具一般要求输出目录不存在或为空。
3. 用拆卡工具把 PNG 拆到 `<卡工程根目录>\<卡名>\`。拆卡不能改原卡：拆前拆后各算一次原卡哈希，确认没变。
4. 独立核对：用装卡工具把卡工程装回成品，再用程序逐字段比较原卡和成品，条目按 id 对齐。卡内容和世界书有任何差异就停下报告。下面两类不算差异：
   - 卡外层的 avatar、chat、create_date、creatorcomment、fav、tags、talkativeness：这是酒馆自己的记录，不进卡工程，推送时酒馆会保留。
   - 世界书条目在文件里的排列顺序：酒馆按 order 和 display_index 排，这两个值不变就不影响。
5. 再核对卡绑定的世界书文件（酒馆数据目录 `worlds\<世界书名>.json`）：逐条比正文、触发词、order、常驻、启用、位置、深度。
6. 建 `记录\`、`候选\`，把核对结果写进 `记录\接卡核对.md`。

### B. 对应旧版（有旧版时）

1. 用程序按正文哈希把新拆的条目和旧版一一对应。旧版正文前如果有说明块（如「## 工序」），先去掉再比，并按第四节先打印确认。
2. 输出对应表，存到 `记录\对应表.md`。每一条归入以下一类：
   - **完全相同**：沿用旧版的类型、名字和说明块里的来源、纠错记录。正文用新拆的，不动。
   - **有差异**：保持新拆的版本；旧版本放进 `候选\<条目名>\`，两个版本都标修改时间，交作者选。
   - **卡里没有**：旧版整份放进 `候选\<条目名>\旧节点.md`，标「卡里没有」。
3. 把文件改名，与条目名对上。改名一次完成，之后只靠名字和 id 认条目。
4. 旧版目录不动，作为资料保留。

### C. 新卡

1. 在酒馆里新建一个空角色，名字用想要的卡名，作为占位。推送需要酒馆里已经有这张卡。
2. 建卡工程目录，名字和卡文件名相同；写卡根 `card.md`。
3. 内容按作者要求和制卡技能写。

### C2. 旧版节点树或散乱草稿：先整理成标准卡工程，再交同步工具

同步工具只认第三节的标准分区。下面两类目录先在工作台整理，不直接交给同步工具，也不在里面补一个空 `card.md` 当卡根。

- **旧版节点树**：有根 `index.md`，或有 `world\`、`character\`、`greeting\`、`output\`、`style\` 下的 `<节点>\index.md`。用迁移工具转到一个新的空目录（见文末「工具对照」）。迁移不改旧目录，正文和工序说明逐字搬运，已有的 id、order、触发设置保留；调研、决策记录、`note\`、`archive\`、`export\` 等资料复制到 `记录\`；解析不了的节点放进 `待归位\`，去处撞车的放进 `候选\`。
- **散乱草稿**：没有开头设置的设定稿、聊天记录里的片段。先按第三节提出归位方案（哪段进哪个字段、哪段拆成哪几条世界书），作者确认后再写；定不下来的放进 `待归位\`，不硬塞。

迁移或整理之后：

1. 读迁移报告里的【缺口】和「与参照成品的差异」，逐条交作者决定。旧目录里有导出成品时，工具拿它补缺失的 order 和卡级设置并逐条比正文，差异只报告不改。
2. 用装卡工具装一次，和旧的导出成品比对；有差异停下报告。
3. 把目录改成酒馆卡名，放进卡工程根目录，再按 E 推到酒馆。

### D. 日常修改

1. 工作台查资料、改内容，产物放进 `候选\`。
2. 作者确认后写进正式文件。说明块里写明来源和确认方式（作者原话、作者裁定或作者限定委托）。
3. 用装卡工具装一次，核对通过后再推。

### E. 推到酒馆

- 推送前告诉作者要推哪张卡、改了哪些条目，作者同意后再推。推送会改动酒馆里正在用的卡。
- 酒馆必须开着。
- 推送前先备份到 `backups\`；工具不自动备份时手动备份。
- 酒馆里有还没拉回的改动时，先拉回，不强制覆盖，除非作者明确要求。

### F. 从酒馆拉回

- 先演练（只看会改什么），再正式拉回。
- 只在酒馆里改了的，直接写回卡工程，写前备份。
- 两边都改了、或酒馆里新增了找不到对应文件的条目：放进 `待归位\`，不覆盖正式文件。
- 处理待归位：把要的内容写进正式文件（或新建文件），然后删掉 `待归位\` 里对应的文件。删掉就算处理完，下次推送以卡工程为准。

## 六、编号

【待定】新增条目的 order 怎么定。默认做法：

- 接来的卡，卡里原有的 order 原样保留，不重新编号。
- 新增条目手写 order，接在同类条目所在号段的末尾。
- 不写 order 时装卡工具可能按类型自动编号，和原有号段对不上；工具报编号警告时，改为手写。

## 七、什么时候停下

- 装回核对有差异
- 原卡哈希在拆卡后变了
- 写入工具拒绝写入目标位置
- 同一条目有两个版本、无法判断用哪个
- 要推送到酒馆，但作者还没同意
- 作者说停止或先纠正

停下时报告：在哪一步、看到了什么、已经做了什么、需要作者决定什么。

## 八、报告

每一步只报告实际执行的命令和看到的结果。写清楚：

- 卡工程的完整路径
- 核对用的是什么方法、比了哪些项、差异数
- 哪些内容进了候选、待归位，各几项
- 有没有推送到酒馆

工具返回成功或核对通过，不等于作者确认了内容。

## 工具对照

上面的流程不绑定具体工具。下表是作者本机现有工具的示例，换了工具或机器时按实际情况替换；表里的命令找不到时停下报告，不猜参数。

| 动作 | 作者本机示例 |
|---|---|
| 拆卡 | card-forge-lab：`node src/cli.mjs unpack "<卡.png>" --out "<卡工程>"`（自带一次装回比对） |
| 旧版节点树迁移 | card-forge-lab：`node src/cli.mjs migrate "<旧卡目录>" --out "<新标准卡目录>"`（输出目录须不存在或为空，不改旧目录） |
| 装卡 | card-forge-lab：`node src/cli.mjs build "<卡工程>"`，成品在 `dist\` |
| 推送 | tt-card-bridge：`node bin/tt-card.mjs push "<卡工程>" "<卡名>.png"`（自动备份；有未拉回改动时拒绝，`--force` 跳过） |
| 拉回 | tt-card-bridge：`node bin/tt-card.mjs pull "<卡工程>" "<卡名>.png" --dry-run`，确认后去掉 `--dry-run` |
