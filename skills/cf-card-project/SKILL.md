# 卡工程流程（v3.2.0）

范围：内容落在哪里、按什么顺序、怎么核对。不管内容怎么写。流程不绑定具体工具，命令见文末「工具对照」。

总规则：

- 卡工程是唯一正式落档的地方，写进卡工程才算数。
- 工作台产物和酒馆里的改动都不直接写正式文件：先进 `候选\` 或 `待归位\`，作者确认后再写。
- 认条目靠名字和 id，认版本靠程序算的正文哈希，数量由程序给出。不靠肉眼、不靠自己数、不抽查。
- 推送、拉回、装卡前先备份。
- 工具返回成功或核对通过，不等于作者确认了内容。
- 标【待定】的项还没有作者决定：按写明的默认做法处理，并在报告里列出。

# 一、三样东西

| 东西 | 是什么 | 管什么 |
|---|---|---|
| 工作台 | 正在用的编辑器或 AI 工具，以及制卡技能 | 查资料、提方案、改内容；产物在作者确认前都是候选 |
| 卡工程 | 一张卡的文件夹 | 正式落档 |
| 同步工具 | 卡工程和酒馆之间的拆卡、装卡、推送、拉回 | 双向同步 |

# 二、位置和命名

```
<卡工程根目录>\<卡名>\
```

- 一张卡一个文件夹，直接放在根目录下，不设作品层。
- 卡名 = 酒馆里卡文件名去掉 `.png`（例：`示例卡.png` → `示例卡`）。推送和拉回靠卡文件名找酒馆里的卡，名字相同才不会推错。
- 酒馆里的卡改名后，卡工程目录同步改名；条目 id 不变。
- 放在工作台能写入的位置。工具拒绝写入（跨盘、目录连接）时停下报告，不用 shell 绕过限制。
- 其他位置的资料只读，正文里写资料路径，不复制进卡工程。
- 名字里有 `[ ]` 时，PowerShell 一律用 `-LiteralPath`。

# 三、分区

```
<卡名>\
  card.md                      卡根：卡名、世界书名、留在卡里的扩展设置
  <字段>.md                    单槽字段（description.md、system_prompt.md 等），空字段不生成
  message\0.md                 开场白（0.md 为 first_mes，1.md 起为 alternate_greetings）
  world_book\**\<条目>.md      世界书条目，可按角色/世界/文风建子目录分组
  regex\<序号>-<名>.json+.html 拆出的正则设置与替换内容
  scripts\<序号>-<名>.json+.js 拆出的酒馆助手脚本、variables.json、xiaobaix-tasks.json
  character.png                封面图
  记录\                        决策记录、出卡单、对应表、核对结果
  候选\                        工作台产物和有分歧的版本，等作者确认
  待归位\                      拉回时酒馆里改了、需要作者处理的内容（工具自动写）
  backups\                     推送、拉回、装卡前的自动备份（工具自动写）
  dist\                        装出来的成品（工具自动写）
```

- 装卡只认：`card.md`、顶层单槽字段 `.md`、`message\<n>.md`、`world_book\**\*.md`、`regex\`、`scripts\`、`character.png`。`调研.md`、`记录\`、`候选\`、`待归位\`、`note\`、`backups\`、`dist\` 不进卡。
- 一条世界书条目一个 `.md`；子目录只用于分组，装卡以文件开头的设置为准。
- 候选写成 `候选\<条目名>\<来源>.md`（例：`候选\示例角色\旧节点.md`、`候选\示例角色\酒馆版.md`）。

# 四、认文件、认版本

| 判断什么 | 用什么 |
|---|---|
| 这是哪一条 | 名字和 id；id（如 `wb-2`）不随改名变化 |
| 是不是同一版 | 程序算的正文哈希 |
| 差在哪里 | 只在哈希不同时看程序列出的差异行 |
| 有多少、对不对得上 | 程序给出的数字 |

- 名字相同不代表内容相同。例：酒馆里的卡和一份旧导出 JSON 有几条同名条目正文不同；只比描述和条目数会误判成同一版。
- 每一项都比。
- 比对前先打印几行程序实际拿去比的内容，确认比的是正文，没有夹带说明块或开头设置。
- 大文件分段读，注明起止行号，读完核对总行数；读取被截断时接着读，不当作读完。
- 哪边更新看修改时间，但不自动选边，列出来交作者。

# 五、流程

## A. 接卡：酒馆里的卡 → 卡工程

1. 确认卡文件名：在酒馆数据目录 `characters\` 下找到 PNG，或用同步工具列出当前卡。
2. 卡工程目录先不建；拆卡工具一般要求输出目录不存在或为空。
3. 拆到 `<卡工程根目录>\<卡名>\`。拆前拆后各算一次原卡哈希，确认没变。
4. 装回核对：装卡工具装回成品，程序逐字段比原卡和成品，条目按 id 对齐；卡内容和世界书有任何差异就停下报告。不算差异的两类：
   - 卡外层的 avatar、chat、create_date、creatorcomment、fav、tags、talkativeness：酒馆自己的记录，不进卡工程，推送时酒馆保留。
   - 世界书条目在文件里的排列顺序：酒馆按 order 和 display_index 排，这两个值不变就不影响。
5. 核对卡绑定的世界书文件（`worlds\<世界书名>.json`）：逐条比正文、触发词、order、常驻、启用、位置、深度。
6. 建 `记录\`、`候选\`，核对结果写进 `记录\接卡核对.md`。

## B. 对应旧版（有旧版时）

1. 程序按正文哈希把新拆条目和旧版一一对应。旧版正文前有说明块（如「## 工序」）先去掉再比，并按第四节先打印确认。
2. 输出对应表到 `记录\对应表.md`，每条归入一类：
   - 完全相同：沿用旧版的类型、名字和说明块里的来源、纠错记录；正文用新拆的。
   - 有差异：保持新拆版本；旧版本放进 `候选\<条目名>\`，两版都标修改时间，交作者选。
   - 卡里没有：旧版整份放进 `候选\<条目名>\旧节点.md`，标「卡里没有」。
3. 文件改名与条目名对上，一次完成；之后只靠名字和 id 认条目。
4. 旧版目录不动，作为资料保留。

## C. 新卡

1. 在酒馆里新建一个空角色占位，名字用想要的卡名；推送需要酒馆里已有这张卡。
2. 建同名卡工程目录，写 `card.md`。
3. 内容按出卡单和制卡技能写。

## C2. 旧版节点树或散乱草稿

同步工具只认第三节的标准分区。下面两类先在工作台整理成标准卡工程，不直接交同步工具，也不补一个空 `card.md` 冒充卡根。

- 旧版节点树（有根 `index.md`，或有 `world\`、`character\`、`greeting\`、`output\`、`style\` 下的 `<节点>\index.md`）：用迁移工具转到新的空目录。
  - 不改旧目录；正文和工序说明逐字搬运；已有 id、order、触发设置保留。
  - 调研、决策记录、`note\`、`archive\`、`export\` 等资料复制到 `记录\`。
  - 解析不了的节点进 `待归位\`，去处撞车的进 `候选\`。
- 散乱草稿（没有开头设置的设定稿、聊天片段）：按第三节提归位方案（哪段进哪个字段、拆成哪几条世界书），作者确认后再写；定不下来的进 `待归位\`。

之后：

1. 读迁移报告里的【缺口】和「与参照成品的差异」，逐条交作者。旧目录有导出成品时，工具用它补缺失的 order 和卡级设置并逐条比正文，差异只报告不改。
2. 装一次，和旧导出成品比对；有差异停下报告。
3. 目录改成酒馆卡名，放进卡工程根目录，按 E 推送。

## D. 日常修改

1. 工作台查资料、改内容，产物放 `候选\`。
2. 作者确认后写进正式文件；说明块写明来源和确认方式（作者原话、作者裁定或限定委托）。
3. 装一次，核对通过再推。

## E. 推到酒馆

- 推送会改动酒馆里正在用的卡：先告诉作者推哪张卡、改了哪些条目，作者同意后再推。
- 酒馆必须开着。
- 先备份到 `backups\`；工具不自动备份时手动备份。
- 酒馆里有没拉回的改动时先拉回，不强制覆盖，除非作者明确要求。

## F. 从酒馆拉回

- 先演练（只看会改什么），再正式拉回。
- 只在酒馆里改了的：写前备份，直接写回卡工程。
- 两边都改了、或酒馆新增了找不到对应文件的条目：放 `待归位\`，不覆盖正式文件。
- 处理待归位：把要的内容写进正式文件（或新建文件），删掉 `待归位\` 里对应文件。删掉即处理完，下次推送以卡工程为准。

# 六、编号

【待定】新增条目的 order 怎么定。默认：

- 接来的卡，原有 order 原样保留，不重编。
- 新增条目手写 order，接在同类号段末尾。
- 不写 order 时装卡工具可能按类型自动编号，和原有号段对不上；工具报编号警告时改为手写。

# 七、停下

- 装回核对有差异。
- 原卡哈希在拆卡后变了。
- 写入工具拒绝写入目标位置。
- 同一条目有两个版本、无法判断用哪个。
- 要推送但作者还没同意。
- 作者叫停或要求先纠正。

停下时报告：在哪一步、看到了什么、已经做了什么、需要作者决定什么。

# 八、报告

只报告实际执行的命令和看到的结果：

- 卡工程完整路径。
- 核对方法、比了哪些项、差异数。
- 进候选、待归位的各几项。
- 有没有推送到酒馆。

# 工具对照

下表是示例；换了工具或机器按实际替换。命令找不到时停下报告，不猜参数。

| 动作 | 示例 |
|---|---|
| 拆卡 | card-forge-lab：`node src/cli.mjs unpack "<卡.png>" --out "<卡工程>"`（自带一次装回比对） |
| 旧版节点树迁移 | card-forge-lab：`node src/cli.mjs migrate "<旧卡目录>" --out "<新标准卡目录>"`（输出目录须不存在或为空，不改旧目录） |
| 装卡 | card-forge-lab：`node src/cli.mjs build "<卡工程>"`，成品在 `dist\` |
| 推送 | tt-card-bridge：`node bin/tt-card.mjs push "<卡工程>" "<卡名>.png"`（自动备份；有未拉回改动时拒绝，`--force` 跳过） |
| 拉回 | tt-card-bridge：`node bin/tt-card.mjs pull "<卡工程>" "<卡名>.png" --dry-run`，确认后去掉 `--dry-run` |
