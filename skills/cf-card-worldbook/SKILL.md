# 世界书

本技能管两件事：世界观写什么（世界节点），以及写好的设定怎样变成按需加载的世界书条目（条目机制）。卡文件装配和导出校验不在本技能。

# 一、世界节点

## 先立世界，再引角色入座

world 是整棵树的地基，而且必须在任何 character 节点之前确认。`references/worldview-template.md` 里的 `worldview_profile` 以通用世界观框架为底，是示例，不是必填表。动笔前先按这张卡的需要提出结构提案：用哪几层、保留哪些子模块、去掉哪些、要不要新增，作者确认后再写。正文用结构化的 key 组织，不写成散文段落；示例里已有合适的 key 就沿用，确需新增时在提案里写明用途。

**题材来源决定用几层**（分诊时判定，先在对话 key 清单中确认；作者批准落盘后才按指定位置登记）：

| 题材来源 | 层 |
|---|---|
| 原创世界 | `world_foundation` + `base_world`，必要时加 `core_rules` |
| 已知作品正传 | `world_foundation` + `base_world`（熟悉部分压缩，决定世界运转的项不省） |
| 已有作品衍生 / IF / 特异二创 | `world_foundation` + `base_world` → `if_divergence` → `core_rules`，三层缺一不可，按这个顺序写 |

- `base_world`：用框架的子模块写原作世界本来的样子——`world_history`、`world_location`、`core_systems`、`special_groups`、`social_structure`，环境偏离常识时加 `environment_features`。它的对象是整个原作世界，不是分支剧情用到的那一小块。
- `if_divergence`：同一套子模块，只写分叉后和原作不同的部分——分歧点与大势、社会变迁、新势力、新据点。
- `core_rules`：本分支独有、全线生效的世界级规则，用作者实例的 `law_name` / `definition`。
- 框架里不归 world 的字段：`narrative_rules`、`style_tags` 归 style；`core_gameplay`、`core_drive`、`core_experience`、`protagonist_focus`、`key_characters` 归规划与 character / output。

**挂树**：合一形态是一个 world 节点放完整的 `worldview_profile`。拆分形态是基底世界节点放 `world_foundation` + `base_world`，分支世界节点（与基底平铺，正文写明从基底分出）放 `if_divergence` + `core_rules`，只在特定场景触发的法则可以再拆成 rule 节点。衍生题材优先拆分，让基底有自己的节点。其余按拆分三问。

**防火墙**：world 管 Where/When/What，也就是地理、历史、法则、物种、大势、全线机制。world 不写任何具体角色的身世、面板、性格、好恶、私密互动。角色在 world 里只能以势力或事件的主导者身份出现，一句客观带过；关于这个人是谁的内容，全部留给 character 节点。反过来，character 不复述世界法则。Do/Don't 对照见模版文件。

**分界五问**：

- 料源对不上先问「这是谁的说法」：是某人的说法就归那张角色卡，照写，不调和。world 只写作者版（客观实际情况），不写「某某说」；原作故意不给答案的，不替原作选。
- 撤一个节点前拆开看：事实本身作者有没有答案？有答案的留在 world；谁怎么讲，归 character。不要把有答案的事实跟着视角一起撤掉。
- 秘密不贴标签：平时会加载的条目只写表面那一层；真相只写一处，放默认关闭的条目（`揭晓/`，`enabled: false`），剧情到了由作者手动打开。角色卡不写「隐瞒」「另有身份」这类暗示——她不知道的事，卡里就不出现。
- 结局只写「有哪些结局、世界变成什么样」；达成条件只留在料源索引备查，写进正文会被模型当成必经路线。

## 节点元信息头

`world_book/**/<条目>.md` 头部元信息（导出时翻译成条目触发配置，字段含义见本技能第二部分和 `references/entry-spec.md`）：

```yaml
---
type: character
keys: [本名, 译名, 绰号]   # 触发词，覆盖聊天里实际会出现的叫法；常驻节点留空
secondary: []              # 二级过滤词（如 module 限 NSFW 语境）
position: before_char      # 或 @D 深度写法
title: 绫音                # 酒馆列表里的标题：自然名称，不重复作品名
constant: false
---
```

order 一般不写，导出时按组自动编号（见「导出规则」第 6 条）；写了就是手动覆盖。

# 二、世界书条目机制

世界书 = 动态字典：聊天最近 N 条消息里扫到关键词 → 对应条目内容注入提示词。核心价值是**大体量设定不占永久 context，按需加载**。

依据：SillyTavern **源码枚举** + 官方文档 + 实卡范本（158 条 entry 的多作品世界卡）逐字段核对。

## 核心规则

- **每个条目独立完整**。激活时单独注入，读不到别的条目；「如前所述」式写法必删。
- **只有 content 进提示词**。keys / comment 都不注入。comment 是酒馆列表标题，用最短自然叫法；只有不加范围会混淆时才补范围，不按目录层级拼标题。标签与标题的命名按卡的装配规则。
- 世界基底设定（世界观、时代、规则）用 **constant 条目**常驻；角色、地点、事件用关键词触发。
- 角色条目的 content 是一段独立完整的人物文本，外层用带名字的 XML 包裹，写明这段属于谁；本节只管它怎么装进 entry、怎么触发。
- **中日文卡必须关 match_whole_words**（全局设置），因为中日文不按空格分词。
- 关键词要覆盖**聊天里实际会出现的叫法**：本名、译名、绰号、称呼（如 `["ナナ", "娜娜", "1-B"]`），不是只写正式名。
- **多角色卡默认双向关递归**（`exclude_recursion` + `prevent_recursion` 都置 true）。范本 158 条中 122 条（77%）如此——角色条里必然提到别的角色名，不关一触发就连锁引爆半本书。只给真正需要链式带出的（地点→驻地角色）开递归。
- 本节只管条目机制，不判定事实来源，也不决定哪种角色说法是客观事实；内容依据与归属由上游查料和节点规划确定。

## 排查

- 条目的机器校验负责 JSON 字段、关键词触发、递归、组、位置、深度和预算，不判断事实依据、人物性格或文体质量。
- 世界书条目出现“不触发”“触发过多”“设定互相打架”等问题时，先分别检查文本表达和机制配置，不把两类问题混为一谈。

## 内容设计原则

- **先审逻辑，再选格式**：每个概念都要有作用、适用范围或限制；没有实际影响的名词、同义重复和只为显得专业的字段删掉。

- **世界书不是特殊文法**：它是按需注入提示词的容器。Markdown/XML/风味 YAML 适合维护和分层；只有需要机器导入、校验或严格输出的部分才要求合法 JSON/YAML。
- **条目按功能分层**：RPG 世界书通常拆为世界基底、时代、地点、组织、角色、事件、机制和场景规则；高频底层规则常驻，低频内容按关键词加载。
- **结构壳不承载核心语义**：开闭 XML 标签或分组标题可帮助模块化，但不能让条目依赖另一个可能未触发的条目才能读懂；每条 content 仍须独立完整。
- **宏先确认来源**：官方宏、预设宏、扩展宏和自定义脚本不可混称。使用 `{{random}}`、`{{roll}}` 等非核心宏前，标明来源并确认目标环境支持；宏失效时不能让整条设定失去意义。

## 决策流程

```
1. 判断形态
   ├─ 附属于某张卡 → 内嵌 character_book（跟卡走，导出即带）
   └─ 跨卡复用/独立世界 → 独立世界书 JSON 文件
2. 列条目清单：世界基底 / 地点 / 角色 / 组织 / 事件 / 剧情 / 设定百科，各自定关键词和 type（事件 `event`、剧情 `plot`、设定百科 `wiki`，归「其余」5xx；机制本身用 `rule`）
3. 逐条定三件事：触发方式（constant/关键词/正则）× 插入位置 × 递归属性
4. 填 content（每条独立完整，外层 XML 包裹）
5. 按 references/entry-spec.md 组装 JSON
6. 交装配环节跑世界书机器校验
```

## 触发方式速查

| 需求 | 做法 |
|---|---|
| 始终在场（世界基底） | `constant: true`（蓝圈），不需要 keys |
| 提到才出现（默认） | keys 数组，多写别名 |
| 需要两类词同时出现 | keys + secondary_keys + `selectiveLogic`。**拿不准就用 0（AND ANY）**；源码枚举是 0=ANY / 1=NOT ALL / 2=NOT ANY / **3=AND ALL**，1 和 3 极易写反 |
| 条目存着但暂不启用 | keys 清空（比 `enabled: false` 温和，想恢复填回关键词即可） |
| 强制激活 / 强制不激活 | content 首行写 `@@activate` / `@@dont_activate`（会被剪掉不进提示词） |
| 模糊匹配/变体 | 把**那个 key 本身**写成 `/pattern/flags`（如 `/娜娜|ナナ/i`）。`use_regex` 字段前端不读，只是兼容位，照写 true |
| 限定使用条件的块（特化文风、成人模块等） | keys 写主关键词，secondary_keys 写场景词，`selectiveLogic: 0`：两组各命中一个才加载。只挂一组关键词，日常戏也会把它带进来 |
| 随机氛围事件 | `probability` < 100 |
| 条目 A 提及条目 B 也触发 B | 递归（默认开）；不想被连锁触发的条目设 `exclude_recursion: true` |

## 插入位置怎么选

| 位置 | 用途 |
|---|---|
| `before_char`（↑Char） | 角色资料、地点、背景设定——范本 85% 条目在这 |
| `after_char`（↓Char） | 补充规则、行为指令——比 before 影响力更大 |
| `@ Depth`（数值 4） | 需要贴近最新对话的状态类信息；depth 小 = 越靠近末尾影响越强 |
| AN 顶部/底部（**2 / 3**） | 配合 Author's Note 用 |
| 示例消息顶/底（**5 / 6**） | 当示例对话块插入 |
| Outlet（数值 7） | 不自动注入，由 `{{outlet::名字}}` 宏手动引用 |

> 🚨 别记反：**2/3 = Author's Note，5/6 = 示例消息**。网上很多资料把这两组写反。

排序：同位置内 `insertion_order` 数值**大的更靠后 = 影响更大**。新卡按组连续编号、不重复：世界 1xx → 人物 2xx → 文风 3xx → 输出 4xx → 开场白及其他（greeting / plot 剧情 / event 事件 / wiki 设定百科）5xx，组内按节点树先父后子（节点不写 order，装配时自动编号）。范本 158 条全是 100，那是旧卡的样子，不照搬。

> 顶层 `position` 字符串只能写 `before_char`/`after_char`；要用示例前后、@Depth、AN 位置，**看 `extensions.position` 数值**（它才是酒馆实际读的）。

## 一张卡到底能挂几本书（分发陷阱）

源码 `getCharacterLore()` 合并了多个来源，**只有前两个能随卡走**：

| 来源 | 存在哪 | 随卡导出 |
|---|---|---|
| 内嵌 `data.character_book` | 卡文件内 | ✅ |
| `data.extensions.world`（主绑定书名） | 卡文件内写名字 | ⚠️ 只带名字，书本体在对方没就失效 |
| `charLore[].extraBooks`（额外挂多本） | **本地 settings.json** | ❌ 不随卡 |
| 全局 `selected_world_info` / 聊天 lore / persona lore | 本地设置 | ❌ |

> 结论：**要发给别人的卡，世界书就内嵌**。用 extraBooks 挂的多本书对方完全收不到，而且不报错——只是默默不生效。同名书已在全局/聊天/persona 激活时会被跳过去重，不会双开。

## 条目上百时的管理招

- **分组标题栏**：插几条 `content` 空 + `keys` 空的条目，comment 写 `ーーーー宇宙人ーーーー`——不注入任何东西，只在前端列表里当分隔线。范本用了 4 条。
- **软禁用**：不想要某条生效又舍不得删，把 keys 清空、内容留着。范本就有一条「避免資料污染未開啟」这么处理。3205 字符躺在卡里但永不触发。
- **comment 别超 100 字**（源码 `MAX_COMMENT_LENGTH = 100`，超了前端截断显示）。

## 常见翻车点

- 一个条目塞整个世界 → 拆。触发精度和预算都会崩。
- 关键词太泛（如「学校」「他」）或只有一个字（如「色」「角」）→ 每轮都触发，等于变相 constant，白吃预算。不用单字关键词。
- 关键词太窄（只写全名）→ 聊天里叫昵称就永远不触发。
- 递归全开 + 条目互相引用成环 → 一次触发半本书。多角色卡默认就该双向关递归，不是事后补救。
- 触发词撞车：同一个词挂在多条上，一喊全响（例：「茶会」同时触发两场茶会）。定 keys 前先在世界书里查一遍重名，常用词改更具体的专名；`check` 的 P22 会报同一关键词挂在多个节点。
- 两种包裹风格（`<Tag>` 与 `[名字]`）混用、每条自造标签名 → 标签名用按节点类型固定的英文小写词，名字写进 `name` 属性，同类多条靠 name 区分（标签表在卡的装配规则里）。
- 忘了每条目独立性 → 条目间互相依赖，单独激活时上下文断裂。
- token 预算：条目总注入量受全局 Budget 限制，超了低优先级条目被挤掉——重要条目 `insertion_order` 给高，或 `ignore_budget`（慎用）。
