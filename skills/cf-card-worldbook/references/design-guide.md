# 世界书设计指南（进阶）

条目怎么切、关键词怎么设、递归/组/时间效果什么时候用。机制字段格式见 `entry-spec.md`。

## 一、条目粒度

一个条目 = 一个可独立提及的实体或主题：

| 类型 | 粒度 | 位置建议 |
|---|---|---|
| 世界基底 | 1 条 constant（世界观+时代+基本规则，压缩写） | before_char |
| 地点 | 一地一条（学校、街区、店铺） | before_char |
| 角色 | 一人一条（内容按戏份定详略） | before_char |
| 组织/势力 | 一组织一条 | before_char |
| 规则/指令类 | 按主题拆，少而精 | after_char（影响更大） |
| 状态/氛围类 | @ Depth，depth 小贴近对话 | position 4 |

切分判据：**这段内容会不会在对方没被提及时也需要在场？** 会 → 拆开；总是一起出现 → 可合并。

## 二、关键词设计

1. **枚举实际叫法**：本名、中/日/英译名、绰号、称呼、班级职务（如「1-B」触发班级相关角色）。
2. **地点触发角色**：常驻某地的角色，keys 里可加地点名——进入场景自动带出人。
3. **别用高频泛词**：「学校」「老师」「他」会把条目变成事实常驻。
4. **正则处理变体**：把 key 写成 `/娜娜|ナナ/` 一条顶多条。识别靠的是 **key 自身的 `/.../ ` 形式**（源码 `parseRegexFromString`），不是 `use_regex` 开关；一旦走正则，大小写/全词匹配选项**全部失效**，需要忽略大小写就自己加 `i` 标志。
5. **次键做场景限定**：主键「温泉」+ 次键「旅行」（AND ANY）= 只在旅行语境下触发温泉旅馆条目。

## 三、递归设计

递归 = 条目 content 里出现的词也能触发其他条目（全局 Recursive Scan 开启时）。

| 目标 | 配置 |
|---|---|
| 提到学校 → 带出学校条目 → 学校条目里的角色名再带出角色 | 两条都不开限制（全 false） |
| 基底条目提到一切，但不想它引爆全书 | 基底条目 `prevent_recursion: true` |
| 某条目只想被直接提及触发，不想被连锁 | `exclude_recursion: true` |
| 隐藏设定：只有其他条目引出才出现 | `delay_until_recursion`：写 `true` 或层号数字（源码按 number 处理，`1` 等价 true，`2` = 第二轮递归才入场）；`0`/`false` = 不延迟 |

### 范本实证：递归默认是“关”不是“开”

158 条的实际分布：

| 组合 | 条数 | 占比 |
|---|---|---|
| `exclude_recursion` + `prevent_recursion` 都 true | 122 | **77%** |
| 两者都 false（参与递归） | 35 | 22% |
| 仅 `prevent_recursion: true` | 1 | 1% |

原因：角色条目写到 `relationships` 就必然出现别的角色名，而那些名字又是别的条目的 keys。递归一开，提一个人 → 带出他的五个朋友 → 每个朋友又带出五个，一轮就把预算吃光。

**写大卡的默认做法**：角色条目双向关死，只给地点/组织类“枢纽条目”开单向递归（它能带出人，人不再带出人）。世界基底 constant 条目同样两者都开，彻底退出递归链。全局 Max Recursion Steps 可限层数（0=无限，1=禁用）。

## 四、Inclusion Group（互斥组）

同 `group` 名的条目同时激活时只插一条。用途：

- **随机事件池**：多条氛围事件同组，按 `group_weight` 随机出一条。
- **状态互斥**：同一角色的不同阶段版本同组，`group_override: true` 时按 insertion_order 最高者确定性胜出。
- **精确优先**：`use_group_scoring: true`，关键词命中多的条目赢（泛条目 vs 专条目共存时用）。

## 五、Timed Effects

| 效果 | 行为 | 典型用途 |
|---|---|---|
| `sticky: N` | 激活后保持 N 条消息在场，期间免概率检查 | 事件/场景展开期间持续在场 |
| `cooldown: N` | 激活结束后 N 条消息内禁止再触发 | 防止氛围事件刷屏 |
| `delay: N` | 聊天满 N 条消息前不可激活 | 中后期才解锁的剧情设定 |

组合示例：随机事件 `probability: 20` + `sticky: 4` + `cooldown: 10` = 偶发、持续一小段、不频繁重复。

## 六、全局激活设置（提醒用户配置，不在 JSON 里）

这些在酒馆前端 World Info 面板设置，卡片作者控制不了但要在发布说明里提醒：

| 设置 | 建议 |
|---|---|
| Scan Depth | 扫描最近 N 条消息，默认即可；条目级可用 `scan_depth` 覆盖 |
| **Match Whole Words** | **中日文卡必须关**，否则关键词永远匹配不上 |
| Recursive Scan | 依赖递归链的卡要求开启 |
| Context % (Budget) | 条目多的大世界卡建议调高，否则低优先级条目被挤掉 |
| Min Activations | 可代替 Scan Depth：向后搜到激活满 N 条为止 |

## 七、content 写法要点

- 条目开头用 `<类型 name="实体名">` 结尾 `</类型>` 包裹（例：`<location name="温泉街">` … `</location>`）——让模型知道这段信息的归属边界。标签名按节点类型固定，名字进 name；范本旧风格 `[实体名]`…`[/实体名]` 新卡不用。
- 条目内部可以直接放一份完整的角色设定（范本多用 `character:` 开头的 yaml），**不需二次改写**。范本 154 条非空中 127 条就是这个形态。
- 台词样本写进角色 YAML 的 `chat_examples` 键，弥补世界书条目没有 mes_example 位置的问题。范本 27 条用 `<角色名_chat_example>` 子标签，新卡不用：包裹内部不再套标签。
- 与卡本体的 description 不重复：卡里有的世界书不写（单一归属）。范本卡本体只有 51 字符，一切具体内容都在世界书里。
- 条目内不写「见 XX 条目」——激活时 XX 可能不在场。

### 单条该写多长

范本单条平均 26,572 字符（主体英文），3万~6万 字符的条目最多（65 条）。但这是**英文**卡：英文 ~4 字符/token，中文 ~1.5 字符/token。写中文卡时同样字符数的 token 开销是它的两倍以上，**单条别直接套这个字符数**。按 token 算：单个角色条目 5k~15k token 是实战范围，同时激活 3-5 个就到预算上限了。
